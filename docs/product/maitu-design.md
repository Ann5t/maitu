# 脉图个人项目推进工作台设计建议

这份建议整理 fudian、project1、Encore、personal-ai-hub 和 the-hive 的已有成果，并根据本次讨论确定一个可实施的首版范围。用户当前最明确的需求是：独立工作能够同时执行；项目历史可在图上看懂；可以从节点直接继续工作并得到结果。

建议以浮点为主干，建立一个以项目图为入口的个人工作台。项目图负责显示目标、任务、尝试、成果和决定，后台服务负责真实执行、调度和恢复。先证明一件实际工作能从输入走到可验收的成果，再扩大能力范围。

本文件保存 2026 年 9 月 30 日的设计建议。当前首版范围以 [脉图首版范围](maitu-scope.md) 为准；部署启动见 [决策 0049](../decisions/0049-maitu-docker-web-bootstrap.md)。本次已读取五个仓库的默认分支源码和主要设计文档；没有运行旧项目的完整测试，也没有进行真实模型调用。文中的代码事实、产品建议和待验证项分别说明。

上述材料显示，有些项目已经打通真实接口，有些主要打通了领域状态和测试夹具。由此可以推断，当前最有价值的工作是把这些层接成一条实际可用的链。仅凭本次静态阅读，不能确定过去每次停滞的具体原因。

## 你日常怎样使用

打开一个项目时，先看到项目图和一句当前情况，例如“两个任务在运行，一个任务需要你选方向”。每个主要节点都有可理解的目标和产出，不要求用户先配置提示词、工具端口或技术参数。

一次典型工作如下：

1. 输入目标并附上资料，例如“整理这五个旧项目，找出能做成自用工具的路线”。
2. AI 根据已有资料提出任务图。节点显示要做什么、用到什么、产出什么、怎样验收；系统标出可以同时执行的节点。
3. 用户修订目标和依赖，启动选中的工作范围。范围内的读取、分析、生成文件和验证可连续推进；范围变化或需要用户决定时，在对应节点等待。
4. 后台同时推进独立节点。图上能看见每项工作正在做什么，或为什么排队、卡住。
5. 点进节点查看结果、输入依据、执行过程和历次尝试。用户可以继续对话、补资料、暂停、重试、开一个替代方案或接受成果。
6. 接受成果后，相关后续任务取得准确版本的输入。关闭页面再回来，图、成果、决定和进度仍在。

这里的“推进”必须产生可检查的结果：文件、代码差异、检索依据、检查报告或一次清楚记录的决定。运行结束与成果已接受是两个不同状态。

## 项目图应当表达什么

推荐默认显示目标和任务的关系，点选后展开该任务的工作现场。图缩小时显示项目阶段和子目标，放大时显示具体工作轮次与成果；底层工具调用和每一条日志进入详情，以保持长期项目可读。

图中至少区分三类关系：

- **属于哪个目标**：帮助理解任务为何存在，形成稳定的项目结构。
- **执行依赖**：说明启动前必须拿到哪项输入；只有这种关系参与调度。
- **来源与沿用**：说明当前方案依据哪个材料、结果或旧尝试，支持追溯和比较。

目标的父子关系可以沿用浮点的目标枝干模型。执行依赖需要独立记录，才能表达“这个任务依赖两条分支的成果”。执行依赖必须无环；返工以新的尝试和版本表达，旧尝试保持可追溯。

用户看到的名称宜直接使用“目标、任务、结果、待决定、历史”。底层 GoalBranch、Session 和整合记录可以继续保留，界面在用户需要时才解释它们。Git 承担文件版本和代码整合，项目图承担用户可读的进展与决定。

每个节点最少显示：任务名称、当前状态、结果摘要和下一步。选中后展开：目标与验收条件、准确输入版本、执行记录、成果和历次尝试。失败或等待必须显示原因和可用动作，例如“等待方案选择”“该服务限流，已排队”“需要补充文件”。

## 并行怎样真正减少等待

多个 API 连接提供了可用执行资源，实际速度仍由任务依赖、服务端额度和本机资源共同决定。系统应显示运行数、排队数和等待原因，使资源利用情况可见。

建议采用完成一项就释放其后续任务的调度方式。例如 A、B、C 同时开始，D 只依赖 A，则 A 完成并满足输入条件后，D 即可启动；无需等待 B、C 完成。这能改进 project1 当前的整批等待方式。

并发策略需要包括：

- 实例、项目和模型连接各自的并发额度；同一服务共享的额度合并计量。
- 持久队列与任务优先级；没有资源时保留任务，等待下次派发。
- 服务限流时按返回信息退避，避免把所有等待变成失败。
- 费用或 Token 上限；达到上限时停止新调用，保留工作现场。
- 独立工作区；两个编码任务并行修改代码时，各自使用 worktree，汇总时检查冲突。
- 已完成结果的收集与版本绑定；失败只阻塞依赖该结果的工作。

用户可用一句话要求“这三个方向一起做”或“这个先做”。后台将其转为明确任务和优先级。涉及已有上游依赖的任务，界面应解释哪些部分可以立即做、哪些仍须等待。

## 历史怎样让人看懂

一个任务拥有多次尝试，每次尝试保存输入版本、执行设置、成果、状态和决定。重试、新方案和目标修订都追加记录，避免覆盖旧结果。

历史视图显示“提出目标 → 第一次尝试 → 得到结果 → 修改方向 → 第二次尝试 → 接受成果”，配以当时的简短说明。用户能选择两个结果版本比较，并看到“当时为什么没继续”“什么变化后值得重开”。

当上游结果改变，后续节点显示“输入已有新版本”。已完成成果保留，同时明确其依赖的旧版本。用户选择继续沿用、创建新尝试或重跑受影响部分，系统不会在用户不知情时替换已接受结果。

图的布局与业务历史分开保存。拖动节点改变位置，不改变执行先后或项目记录。增加新节点时尽量保留已有位置；大项目支持折叠子目标和聚焦正在推进的区域。

## 推荐的实现边界

延续浮点现有的 Rust、Axum、PostgreSQL 和 Git/worktree 基础，采用一个长期运行的后台服务。浏览器断开与任务取消分别处理；后台执行进度通过有序、可补齐的事件流更新界面。在部署偏好尚未确认时，先按本机可启动设计，并保持同一后台可部署到自有服务器。关闭网页后任务可以继续；关闭电脑后仍要继续，则需要将后台放在持续运行的服务器上。

首版先选一个已有 API 连接完成真实文本任务，再加入第二个连接验证跨连接调度。Provider 接口负责请求、流式响应、取消和用量，项目状态、上下文与历史由浮点保存。

编码节点可以接成熟执行器。当前官方 Codex App Server 提供自定义客户端所需的对话、事件和操作决定接口，适合作为可替换的执行适配器候选；首个试验宜采用本地 stdio 连接，并固定运行时版本。Claude Agent SDK 和 ACP 可以作为后续候选，需分别验证认证、工具控制和会话恢复能力。

浮点原有决定 0045 提出了 Rust 自有 Agent 核心与 Pi Provider Driver 路线。继续这条路线需要实现完整工具循环和恢复机制；接成熟执行器则能减少首版执行层的工作量。两条路线应通过同一组真实任务比较后选择。这份建议没有改变原决定，也没有验证用户账号对某个模型或 SDK 的可用权限。

前端先让现有工作台展示真实执行状态和成果，并支持从节点启动与继续。画布增强可以独立推进，避免把真实执行的交付绑在整个前端重写上。现有 Leptos 画布方案可继续评估；React Flow 是已有自定义节点、连接和平移缩放能力的替代候选，换前端需要明确验证收益后决定。

## 首个可用版本的范围

首版保留四个主要入口：项目、项目图、待我处理、设置。节点内包含对话、资料、执行记录和成果。收集新想法作为轻量入口，复用 Personal AI Hub 的判断和明确下一步流程。

首版必要能力如下：

| 能力 | 用户可观察的完成条件 |
| --- | --- |
| 真实执行 | 节点调用已配置模型，使用指定资料，形成实际可打开的成果 |
| 可靠并行 | 三个独立任务的执行时段重叠；资源不足的任务保持排队且最终执行 |
| 正确依赖 | 后续任务读取指定上游成果版本；依赖满足即获调度资格 |
| 图上推进 | 在节点上启动、暂停、继续、重试和开替代方案；状态与后台一致 |
| 清晰历史 | 历次尝试、结果和接受理由可查看；重新运行后旧结果仍可追溯 |
| 恢复 | 关闭网页后后台继续；服务重启后能识别中断任务并恢复或明确等待核对 |
| 文件使用 | 文本任务读取用户指定材料；编码任务在隔离工作区形成可检查差异 |

先将新插件市场、多人权限、全媒体生成和更多通信渠道留到实际需求出现后。已有模块与历史设计保留，交付顺序由首个完整使用流程决定。

## 实施顺序和验收

**第一段，验证一个节点的真实执行。** 接入用户已有的模型连接，将目标、输入、流式过程和文件成果记录到一个工作轮次。完成后，用户应能从节点打开真实文件并继续同一项工作。

**第二段，验证并行与依赖。** 同时运行三个独立资料整理任务，再增加一个只依赖其中一个结果的后续任务。核对资源不足时不丢任务、完成一项即可释放相关后续任务、失败不拖住无关分支。

**第三段，验证图与历史。** 将真实任务显示到项目图，支持选中节点操作。对同一任务创建第二次尝试，比较两版成果并记录选择理由。刷新和重新打开后，这些信息保持一致。

**第四段，验证编码和恢复。** 接入一个编码执行器，在独立 worktree 完成小修改与检查，展示结果并由用户决定是否纳入项目。进行服务中断恢复试验；具有外部副作用的动作不能因重启被盲目重复。

第一段完成就交付一个可实际使用的节点。每段以真实文件、请求记录和可重现的使用流程验收，单独的接口测试或占位页面不能证明日用能力。

建议首个试用项目使用这五个仓库本身：并行完成可复用代码清单、当前执行缺口清单和界面操作建议，再汇总为首版实施任务。这样可以同时检验材料读取、并行、依赖、图上操作和成果追溯。

首轮连续使用时重点记录：哪些等待本可避免、多少次需要重复解释项目背景、返回项目时能否立即理解现状、产出的文件是否实际用上。这些记录用于决定下一项功能，而不是根据页面数量判断进度。
