## 最终要完成的使用流程

用户说出一个想法或选中已有项目，脉图读取指定资料和代码，提出可修改的推进图。用户能理解每个节点的目的、依赖、成果和下一步，并在节点内补充要求。独立任务利用可用的模型连接和工作区同时执行，形成真实文件或代码改动，完成检查后供用户选择采用。

第二天重开项目时，图上能直接回答：已经做了什么，为什么停在这里，哪些任务还在工作，哪些需要用户处理，采用的是哪一版成果，以及接下来可以推进什么。Git 保留代码历史；图上的记录让用户理解过程和决定。

持续使用以这个完整流程验收。模型提出文件修改或检查建议时，程序必须真的执行并记录结果；模型的描述不能代替工具结果。

## 开发阶段与验收条件

下面是建议的交付顺序。阶段完成需要对应的真实使用证据；阶段中的代码存在或界面出现，不能单独算通过。优先级可随用户的实际使用问题调整，整体目标保持不变。

| 阶段 | 当前状态 | 交付行为 | 通过条件 |
| --- | --- | --- | --- |
| 0 资料执行基础 | 首轮已验收，交付已进入主线 | 文本资料、真实 DeepSeek 请求、并行任务、固定成果版本与历史 | 已有三请求重叠、下游使用确定版本、失败隔离和容器重建证据 |
| 1 真实编码工作流 | 本机真实验收通过，任务分支交付 | 导入代码项目，在独立工作区读代码、改文件、运行检查、根据失败修正，图上查看差异并采用 | 一个真实小功能从要求到可采用补丁完成；记录实际命令和退出状态；至少两个独立编码任务互不污染 |
| 2 从想法到项目图 | 本机真实验收通过，任务分支交付 | 目标生成可编辑的推进建议，校验依赖后形成节点；节点内补充要求，修改方向或创建替代尝试 | 一个自然语言目标形成能执行的图；用户能修改后继续；每项都有具体成果和验收要求，缺资料时说明缺什么 |
| 3 多连接与资源调度 | 已完成真实验收，任务分支交付 | 管理多个 API 连接，为任务选择连接，按任务、模型额度和工具资源排队，显示实际用量 | 可用连接之间真实调度；额度用尽的连接不挡住其他连接；排队不丢任务；限流退避、重试次数和预算有界 |
| 4 日常使用与项目历史 | 已完成真实验收，任务分支交付 | 图的缩放、聚焦和布局保存；比较尝试、记录采用理由、显示过期输入；暂停、取消与恢复；集中查看需要用户处理的事 | 用真实项目完成两轮需求迭代，离开后再进入能理解现状；一次失败或中断后继续，已接受成果和操作记录不丢、不被覆盖 |
| 5 五库内容收拢 | 已完成迁移、独立恢复验收与末尾核对 | 值得继续的能力迁入现行代码，其余原实现和资料保留为来源归档；完整历史与仓库附属资料可从脉图恢复 | 每库都有内容清单、迁入去向、校验值和空目录恢复记录；已迁入能力按脉图的真实使用流程验证 |
| 6 发布可日用版本 | 核心流程已验收；长期日用与用户试用接受待积累 | 可重复启动、升级、备份和恢复，记录使用边界与待修问题 | 上述使用流程通过；影响核心使用或造成数据损失的问题已处理；用户试用接受后，才建议删除已完成迁移验收的旧库 |

用户选择阶段 1 和 2 都做，已形成[从想法到编码成果 Goal](../development/code-workflow-goal.md)，连接目标生成、任务图、实际工具执行与成果采用。阶段 3 和 4 会继续使用阶段 0 的队列、依赖和 Attempt 历史，避免另建彼此脱节的执行系统。

阶段 4 的两轮迭代是建议的最小使用验收：第一轮完成一个实际改动，第二轮补充或改变要求并继续同一项目，同时安排一次失败或中断。它不等于长期稳定性保证；没有实际使用证据时，仍标为待验收。

## 本轮目标与编码交付

[从想法到编码成果 Goal](../development/code-workflow-goal.md)定义本轮输入、计划编辑、工具范围、输出和验收。实际用脉图前端组件副本完成筛选、统计和整合代码，详见[实施进度](../development/maitu-progress.md)。这些组件尚未接入网页筛选入口，不能把代码验收当作该页面功能已经上线。

一项编码任务必须留下基线提交、输入要求、模型请求、工具调用结果、文件差异、实际检查结果和采用决定。并行任务使用各自的工作区；整合任务等待所需成果，在新的整合现场检查冲突并运行验证。

连接配置保留用户当前的 DeepSeek、思考模式与长度设置。工具执行接入现有 Rust 与工作区基础，接入选择要先验证已有代码的适用边界。Flutter、前端整体重写和新的插件市场暂不成为这条使用流程的前置条件。

## 五个旧仓库怎样进入脉图

功能迁入和内容保存分别记账。被替代的旧实现仍需可恢复；只挑选有用代码不足以支持删除原库。所有可访问分支、提交和当时存在的附属资料按[迁移与删除准备](../operations/legacy-repository-migration.md)保留。原始 Git 对象保留 SHA，来源清单能定位原仓库、分支、路径以及采用理由。

| 来源 | 进入现行产品的主要方向 | 必须保留的来源 |
| --- | --- | --- |
| 浮点 | 目标和工作轮次、上下文、worktree、持久调度、检查与整合基础 | 默认分支与另一条基线分支的历史、设计、工具与部署资料 |
| project1 | 模型接口、工具注册、会话执行；按现有队列改进并行编排 | 全部分支与 PR 资料；不能把旧整批等待逻辑直接当作可靠依赖调度 |
| Encore | 输入、判断、决定、结果回流；开发分支中的 Provider 管理、来源时间线、对话与数据导入导出 | 默认分支和其他开发分支的原实现与设计 |
| Personal AI Hub | 想法收集、判断稿、验收、复盘、项目上下文 | 全部工作流分支及其资料；判断草稿功能与真正执行分别验证 |
| the-hive | 目标拆分、任务分配、Worker 与模型选择 | 原始拆分、派发和执行资料；依赖错误、资源占满时漏派等行为不能沿用 |

这些方向来自源码静态阅读，是复用候选。迁入前检查对应分支的实际实现，迁入后验证最终行为；不会以“旧库里已经有代码”代替验收。

原源码、历史设计和未采用实现保留在同一脉图仓库的来源档案中。完整 Git bundle 和需要保留的大型原件进入本仓库 Release，清单在源码中保存下载位置、SHA-256 和恢复方法。Maitu 保持一个实际运行的产品入口，各原库不作为五个并列应用长期启动。

## 怎样判断可以收尾

“软件完全没问题”通过具体使用范围表达：本文中的资料工作、目标推进、编码与检查、并行、多连接、历史和恢复都实际工作；测试或试用发现的问题如实保留，不承诺不存在尚未发现的缺陷。

产品达到日用条件后，每个旧仓库还要单独通过迁移验收。能够从脉图取得该库的来源内容和历史，在空目录恢复并核对，再给用户该库的删除准备结果。开发完成、迁移完成和用户删除决定是三个独立状态。当前五库均未达到删除条件，原库继续保留。

没有完成的一段继续保留在本路线中，不因某轮 Goal 结束、PR 合并或界面节点变绿而从整体目标中消失。
