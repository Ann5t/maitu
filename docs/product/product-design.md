# Fudian 产品设计基线

- 文档版本：0.2
- 基线日期：2026-08-22
- 状态：讨论中；2026-08-23 之后的目标图、Git/LFS 与工具系统讨论尚未完整回填
- 适用范围：Fudian 第一版及其后续 Goal、实现、测试与评审

## 1. 文档用途

这份文件记录 Fudian 的长期产品约束，不是某一次开发任务的待办清单。

后续每个实现 Goal 都必须引用本文件。Goal 可以选择本阶段要实现的子集，但不得在没有记录新决策的情况下悄悄改变这里已经确定的语义。新的讨论可以修订本文件；旧结论应保留在版本历史中，而不是只存在于聊天记录里。

当前工程就是 Fudian 的第一版。遗失工程、历史 Docker 镜像、数据库名称和界面资料只作为取证与设计参考，不构成产品前代，也不产生运行数据兼容义务；产品界面中不形成“桌面版 / Docker 版 / Rust 版 / nextgen”等版本叙事。`Rust` 只描述技术栈；内部 schema、协议或 BranchProposal 的 `v0.1` 等编号也不等于产品版本。

[`architecture/architecture.md`](../architecture/architecture.md) 描述当前已经实现的技术状态；本文件描述要建设的产品。两者不应混为一谈。

## 2. 一句话定义

Fudian 是一个单用户、自托管、面向长期目标推进的项目执行系统：用户提出意图，AI 与用户逐步形成目标，多个 Agent 通过目标枝干进行探索和产出，所有结果带着证据与来源回流，最终由用户决定是否接受、合并和完成。

它不是通用笔记软件、普通任务清单或以聊天框为中心的 AI 助手。

## 3. 顶层信息架构

产品存在两个一级空间：

- **想法**：项目的上游，用来收集、发展和筛选尚未形成项目的意图。
- **项目**：目标开始被正式推进后的运行空间。

想法空间的完整布局仍延后，但从想法开始项目的边界已经确定。用户在原对话中接受当前 ProjectProposal 版本，表示授权系统正式投入工作；系统随即创建 Project、该项目的独立 Git/Git LFS 仓库、根 GoalBranch、目标说明 v1 和首个 Session。不会先创建空项目，再要求用户批准一次根 BranchProposal。

想法不需要成熟到能够预先给出最终方案。ProjectProposal 可以把项目定义为交付、探索或混合工作，并诚实保留未知项；用户尚不想让系统投入正式工作时，就继续留在原想法对话中。项目创建后，来源想法和被接受的准确版本继续作为只读来源记录。

## 4. 已确定的核心术语

### 4.1 Project

项目是稳定的身份、独立 Git/Git LFS 仓库、总目标和生命周期容器。项目由获批 ProjectProposal 直接启动，包含一条根目标枝干以及由它递归展开的子目标枝干。

### 4.2 GoalBranch

**一个目标对应一整条枝干。**

目标枝干持有：

- 当前版本的目标说明；
- 从父枝干继承的上下文、项目文件和 Evidence 引用；
- 唯一且持续存在的 Git branch，以及需要时挂载的 worktree；
- 依次发生的 Agent Session 节点；
- 子目标枝干、回流成果与审核记录；
- 当前状态和未解决条件。

一个正式 GoalBranch 严格对应一个 Git branch。根 GoalBranch 直接使用项目默认分支；子 GoalBranch 在 Proposal 获批后，从父 Session 的准确安全 commit 创建。BranchProposal 本身没有 branch 或可写 worktree。

Git branch 是长期身份，物理 worktree 只是可重建的运行现场：活动时挂载，暂停或归档后可以释放，需要时从已记录并现场核验的 commit 重建。同一目标枝干同一时间只允许一个 Agent 修改其 worktree。需要并行时，必须先提出并批准新的子目标枝干。

运行中的 GoalBranch 必须位于目标树的执行前沿：一条枝干只要存在运行中的后代目标，就不能同时运行自己的工作 Agent。父 Session 在子枝干开始前形成安全 commit、释放写租约并进入等待；并行工作由兄弟子枝干表达。父目标尚未完成的主线若要并行继续，也应形成边界明确的子目标，而不是由父 Agent 一边协调一边修改文件。

父枝干等待期间可以由受控整合流程接收已经审核通过的子枝干 merge，因此其 Git HEAD 可能前进，但这不等于父工作 Agent 正在执行。只有必需子目标均已接受、明确失败或被用户有理由地豁免，且没有运行中的后代后，父枝干才能创建下一 Session 恢复整合和推进。

GoalBranch 进入 `integrated | stopped | archived` 等终态后，其 Git ref 保留并由 Fudian 设为只读，继续指向最终 HEAD；物理 worktree 在确认没有活动租约或整合任务后释放。Git 和 Git LFS 对象继续可达，因此现场可以按原 commit 与环境记录重建。若以后要从旧成果继续，创建来源清楚的新 GoalBranch，不重新激活已经结束的枝干。

### 4.3 AgentSessionNode

**一个 Agent Session 是目标枝干上的主要节点。**

Session 内部可以包含大量行动、小目标、命令、测试、浏览器操作和轻量检查点；这些内容进入 Session 的详情与事件记录，不自动成为项目主图上的主要节点。

一个执行进程崩溃后恢复，仍属于同一个 Session 节点。只有审核退回后开始新一轮工作，或明确重新分配一轮工作时，才在同一枝干上创建下一个 Session 节点。

同一 GoalBranch 上的 Session 连续接力。后一个 Session 必须从前一个 Session 的最终安全 commit 开始，不回到父枝干或初始基线；Session 切换不创建 branch，也不发生 merge。前一个 Session 的有意义文件变化必须在交接前形成干净的检查点 commit，不能依赖某个未提交的物理目录继续存在。

审核退回后的新 Session 默认继承被冻结候选的完整状态，再根据反馈继续修改。需要放弃旧变化时，以新的修改或 revert 保留历史，不通过重写历史假装旧工作没有发生。一个 Session 可以产生零到多个 commit；Session 和 commit 不是同一种节点。

### 4.4 Proposal 对话与 BranchProposal

所有 Proposal 都是其来源对话中的特殊版本化消息，不是把用户带离现场的独立审批页面。AI 在当前对话中生成一张简洁提案卡；用户同意就接受准确的当前版本，不同意则直接继续聊天，AI 根据反馈生成下一版本。旧版本折叠保留，过时版本不能再接受，详细字段按需展开。

接受后，本次 Proposal 讨论关闭为只读历史，并原子执行对应转换；只有这时界面才进入新项目、新目标枝干或新的目标说明版本。放弃整个提案可以显式取消，但普通修改不需要先点击“拒绝”或“退回”。ProjectProposal、BranchProposal 和目标说明修订 Proposal 都遵循这一交互。

创建目标枝干前统一使用 `BranchProposal`，不强制存在“第零号节点”。

BranchProposal 记录：

- 为什么需要这条枝干；
- 目标说明草稿；
- 已知约束和未知问题；
- 期望返回父枝干的结果；
- 探索与停止方式；
- 需要用户判断的时机；
- 上下文继承点和工具需求。

BranchProposal 出现在父 Session 的原对话中，不因此变成 Agent Session 节点。用户接受当前版本前不启动执行 Agent，也不创建正式可写 worktree。

目标说明不是与 GoalBranch 并列的对象，而是 GoalBranch 内部的版本记录。BranchProposal 中保存说明草稿；用户批准后，同一内容成为新枝干的 v1。以后修改只新增不可变版本并切换当前版本，不创建新 GoalBranch，也不覆盖旧 Session 当时采用的说明。

### 4.5 候选成果摘要与 Evidence

- `候选成果摘要`：工作 Agent 在拟合并时自动生成的简短结果列表，作为冻结候选的一部分引用准确的 Git commit、路径和 Evidence。
- `Evidence`：支持、反驳或阻塞目标判断的结构化观察与测试结果，并绑定准确的 Git commit、项目文件路径、工具调用或外部来源。

候选成果摘要不是独立领域对象，没有单独生命周期，也不能被逐项选择或合并。用户不需要填写；需要修改时退回枝干继续工作，并在下一次拟合并时冻结新摘要。子枝干只有在整体可接受时，才通过标准 Git merge 回到直接父枝干。

Evidence 默认由 Runner、工具调用、测试、浏览器和 Git 操作自动生成：系统记录命令或动作、结果、时间、准确 commit、环境和内容引用，Agent 与用户都不需要填写 Evidence 表。外部观察或主观判断可以在自然对话中给出，再由系统结构化并保留原话来源。需要长期保存的日志、截图和 Trace 进入项目 Git/Git LFS；Evidence 只保存可查询事实和准确引用。

文件、图片、报告、数据集、代码和需要长期保留的浏览器 Trace 都是项目仓库中的普通 Git 或 Git LFS 内容，不再抽象成独立的 Artifact 版本历史。Evidence 只索引并解释这些内容，不复制文件；没有保留价值的运行输出属于临时数据。

工作过程中的长篇结论写入项目仓库，轻量进度留在 Session 事件中。枝干未进入拟合并就停止时，只在 Session 和 GoalBranch 上保存终止摘要，不补造 Contribution。

### 4.6 MergeGate

`MergeGate` 是枝干回流处唯一的合并关口，也是图上唯一的菱形对象。从工作 Agent 提出完成开始，到父枝干真正更新或候选被退回为止，都属于同一个 MergeGate。

冻结候选、隔离整合尝试、冲突处理、测试、独立 AI 审核、用户对话与决定都是 MergeGate 内部的阶段和追加式记录，不作为并列的 `MergeCandidate`、`ReviewGate`、`ReviewDecision` 或 `Integration` 暴露。父 HEAD 变化时可以在同一 Gate 内生成新的整合尝试；枝干被退回并继续修改后，下一次拟合并才创建新的 MergeGate。

菱形的默认审核卡只显示“改了什么、验证通过什么、仍有什么问题、需要用户判断什么”。测试日志、截图、Trace、diff、完整 Evidence 和审核推理按需展开，不在第一层铺满页面。

## 5. 项目执行循环

### 5.1 从意图到执行

1. 用户用自然语言表达想做的事，可以只是一句话。
2. AI 根据父枝干上下文整理 BranchProposal 和目标说明草稿。
3. AI 只询问会实质改变方向、权限或可执行性的关键问题。
4. 用户在原对话中接受当前 Proposal 版本。
5. 系统从准确的父节点快照创建目标枝干、worktree 和第一个 Agent Session。
6. Session 在自身边界内自主推进。

ProjectProposal 使用同一原则，但接受后直接创建项目仓库和根 GoalBranch，并把首个 Session 持久化为已开始或等待调度；根目标不再经过第二个 BranchProposal。系统资源暂时不足只会让该 Session 可恢复地排队或暂停，不把项目降级成需要再次批准的空壳。

### 5.2 Session 的正常出口

Agent 没有达成枝干目标时：

- 如果仍能自行推进，就继续当前 Session；
- 如果目标太大或需要并行，就提出拟分支并暂停；
- 如果需要用户的品味、科研判断或方向选择，就请求判断；
- 如果缺少外部条件或无法安全继续，就异常暂停。

只有当工作 Agent 认为**整条目标枝干的目标已经达成**时，才能提出拟合并。拟合并不是阶段汇报，也不是已经发生的合并。

子枝干发现更多工作时，属于自身目标范围的继续向下拆分；实际属于祖先目标范围的，向正确祖先登记新的兄弟目标草稿并让该草稿进入等待用户批准状态。创建和审批草稿不要求重新启动祖先工作 Agent。

### 5.3 拟合并与退回

拟合并时冻结候选现场，包括准确的 Git 状态、项目文件、Evidence、环境版本和测试结果。

- 子枝干先在隔离 worktree 中形成完整 Git merge 候选；根枝干没有父级整合，只形成候选完成现场；
- 独立审核 AI 检查最终候选结果；
- 等待决定期间，用户可以继续向该枝干最后一个 Session 的 Agent 和审核 AI 追问信息，但对话不能修改冻结候选；需要改变文件时必须退回；
- 用户最终决定接受、提出部分接受意见并退回整理、退回或放弃；
- 目标条件仍有未满足、未验证或依赖主观判断的部分时，用户可以在看见明确警告后决定本次例外接受；系统保存原始决定及例外项，但不强迫用户填写额外表格；
- 候选身份不确定、实际内容与审核对象不一致、必要 Git/LFS 对象缺失或授权失效等完整性错误不能被例外接受，必须先重新形成可确定的候选；
- 未经用户接受，候选结果不得影响父枝干；
- 退回后，根据用户与 AI 的讨论在同一目标枝干创建下一个 Session 节点继续；
- 部分接受只记录已认可内容和仍需修改的反馈，不执行物理合并；Agent 先在原枝干继续整理，或在合并前提出新的子目标进行拆分；
- 整体接受后，系统以 compare-and-swap 把已经审核的标准 merge commit 发布到直接父枝干；不 cherry-pick、拼补丁或另造文件合并协议；
- 候选成果摘要、Evidence 和审核记录随整枝合并结果建立来源关系，父 Session 随后恢复或开始新的整合 Session。

每次整合尝试都从当时的父安全 HEAD 建立隔离 worktree，执行标准 `git merge --no-ff` 并重新验证。Git 冲突按 Git 的正常冲突语义处理；Fudian 负责暂停、展示冲突、安排受控整合和保存审核记录，不自行发明另一套冲突算法。父 HEAD 在发布前变化时，该次尝试失效；系统在同一 MergeGate 中重新形成候选、复验并再次等待用户决定。Git 是文件内容、提交历史、diff 与 merge 结果的权威来源；PostgreSQL 只保存领域状态、Git 引用及冻结对象 ID 作为映射和证据。

没有 Git 冲突也必须重新构建和测试；发生冲突时，由 Gate 内有写权的整合 Agent 只在隔离候选中完成三方合并，再交给另一个只读的独立审核 AI 复核。无法在不作主观选择的情况下形成候选时，Gate 先请求用户判断；这不是最终批准，候选完成并复核后仍需用户决定。用户批准最终候选后，系统才可以更新父 branch。

普通 Git 与 Git LFS 经过同一 Merge Gate。文本由 Agent 结合 base、父版本和子版本处理；只有存在相应格式插件时，Agent 才能尝试二进制语义合并。无法理解或自动融合的文件必须明确给出保留父版本、保留子版本、两份并存或人工重制等选择，不能伪造成功。若冲突处理已经成为独立的大目标，则撤回候选，回原子枝干创建新 Session 或继续拆分。

多个兄弟子枝干只在没有已知前置依赖时并行。任一子枝干通过审核并被用户接受后立即 merge 到直接父枝干，不等待其他兄弟完成。仍在运行的兄弟保持原创建基线，不被系统自动 rebase、reset 或 merge；父枝干的推进由受控整合流程完成，不启动父工作 Agent。父更新怎样通知和同步给其他枝干由独立规则约束。

根目标没有父枝干，因此对应的是“候选完成”。AI 可以提出候选完成，只有用户可以最终确认项目完成。

### 5.4 暂停类型

用户界面必须区分：

- **等待拟分支审查**：Agent 认为需要拆出新的目标枝干；
- **等待判断**：当前目标需要用户的直觉、品味或科研判断；
- **等待拟合并审查**：Agent 声称枝干目标已经达成；
- **异常暂停**：工具失败、缺少条件、预算耗尽或无法安全继续；
- **手动暂停**：用户主动停止当前执行。

暂停后，原 Session、目标草稿、MergeGate 或工具请求本身必须进入持久的等待用户状态，并主动通知用户，不能只写日志或另造一份权威待办状态。

“待我处理”是对所有真实等待状态的汇总视图，不是独立业务对象。每个来源对象保存原因、最后安全检查点、已尝试办法、风险、需要用户做什么、建议动作和恢复条件；用户处理时直接更新该对象。系统可以维护可重建的查询索引，但不能用单独 AttentionItem 决定工作是否仍在等待。

## 6. 成果与完成语义

每条目标枝干都包含版本化目标说明。目标说明可以同时包含：

- 想达到的外部结果；
- 明确的硬约束；
- 主观偏好；
- 当前未知问题；
- 不做什么；
- 验证或探索方法；
- 何时请求用户判断；
- 停止条件与回流方式。

状态语义严格区分：

- **完成**：证据满足当前目标说明，且用户最终确认；
- **停止**：用户明确放弃继续推进，原因和已有成果保留；
- **等待**：缺少外部条件，并记录恢复条件；
- **归档**：只是一种存储与展示状态，不代表成功或失败；
- **枝干失败**：不等于项目失败，负面结论也可能是有效结果。

AI 无权自行确认根项目完成。

## 7. 最低充分明确度

结构化是系统的负担，不是用户的填表任务。

用户默认通过自然语言、文件、图片或语音表达意图。AI 负责在原对话中生成结构化 Proposal 卡片；用户只审核简短的目标方向、关键边界、重要推断和需要判断的事项，详细字段按需展开。反馈继续使用自然语言，不要求填写“退回原因”表单。

目标说明不追求虚假的“全部明确”，而追求最低充分明确度：

- 已知且稳定的部分明确记录；
- AI 推断的部分标注为推断；
- 不知道的部分诚实标注为未知；
- 低风险未知可以通过探索逐步收敛；
- 会实质改变范围或方向的问题必须找用户；
- 执行 Agent 不能自行降低或偷偷修改当前目标说明，只能提出新版本草稿。

用户在使用过程中的灵感和感受可以持续形成目标说明修订建议。只有用户确认后，它们才成为正式的新版本；GoalBranch 的身份、Git branch 和已有 Session 历史保持不变。

## 8. 探索型与主观型目标

设计和科研目标可能无法在开始前定义最终效果。此时目标说明应定义探索过程，而不是伪造结果标准：

- 当前意图和方向；
- 已知硬边界；
- 尚未确定的问题；
- 要制作的原型、实验或候选方案；
- 预算和停止条件；
- 何时请求用户体验或判断；
- 谁拥有最终判断权。

一次探索即使否定了原假设，也可能成功完成目标，因为它减少了不确定性。系统可以保证所有已经发现的依赖、假设和未解决项不会被悄悄遗漏，但不能声称已经排除科研中的所有未知未知。

## 9. 上下文与记忆

每条子枝干继承父节点的全部可用项目文件和上下文，但不把全部历史同时塞入模型窗口。

同一 GoalBranch 创建下一 Session 时，上一 Session 的完整对话和来源永久保留，但默认模型窗口只装入当前目标说明、不可折叠的硬约束、已经确认的决定、上次交接摘要和当前工作相关文件。完整旧对话仍在来源目录中，可以由 Agent 按需检索和读取；摘要不能成为丢弃原文的理由。

上下文采用按需披露、渐进式披露：

1. 默认提供当前目标说明、权限边界、当前状态和当前节点；
2. 提供继承的决策、项目文件和 Evidence 目录；
3. 根据当前工作加载相关摘要与片段；
4. Agent 需要验证细节时读取完整原文、文件和日志。

目标、硬约束和权限边界永远不会被折叠。摘要、全文索引和向量索引都是可重建的辅助层，不是权威事实来源。

每个 Session 默认可见整个 Project 的目标枝干地图，包括枝干名称、父子关系、状态和简短进度。已经审核并 merge 的成果可以作为正常项目上下文读取；其他活动枝干的未审核文件和完整对话不自动进入上下文，也不能通过项目地图绕过枝干隔离。地图中的简短进度只是被动状态投影，不引入项目级 Coordinator、点对点 Signal 或未审核成果广播。

重要结论必须写成带来源的结构化记录，并能追溯到节点、Evidence、准确的 Git commit 与路径或外部资料。外部网页始终是不可信资料，不能成为系统指令。

子枝干获批并合入父枝干后，系统向仍基于旧父 commit 运行的直接子枝干提供轻量父更新通知。通知由真实 merge commit、被冻结的候选成果摘要和 Evidence 推导，只默认披露来源目标、摘要、改变路径和证据目录；完整 diff、文件和证据按需读取。数据库只记录通知的投递、读取和处理状态，不复制另一套成果历史。

接收 Agent 可以忽略与目标无关的更新，或在安全 commit 后显式把父枝干 merge 到自己的枝干。系统不得自动 rebase、reset 或修改接收方 worktree。检测到修改路径重叠时，接收方在下一个安全点先评估；实际冲突进入明确的冲突处理流程。

用户可以在 Session 运行中继续发送消息。普通消息进入该 Session 的持久输入队列，由 Agent 在下一个安全动作边界读取并调整；消息不会在一次文件写入或不可分割工具动作中间篡改执行状态。用户选择“立即暂停”时，系统要求当前行动尽快形成文件与 Git 安全检查点，然后把同一 Session 置为手动暂停并明确告知已经停在哪里；恢复不会创建一个冒充新工作的 Session。

## 10. 自主权限与安全边界

Session 在批准的目标枝干内自主执行，不逐次请求用户许可。跨枝干影响只能通过 Proposal、审核与真正合并发生。

工作区与执行安全遵循：

- 父级快照只读，当前目标枝干可写；
- 除项目地图中的被动状态摘要外，不允许读取或修改其他活动枝干的未审核内容；
- 不暴露宿主机用户目录、SSH 密钥、私人浏览器资料或容器运行时 Socket；
- 公共互联网可以用于搜索和浏览；
- 登录私人账号、发送消息、部署、付费和其他外部写操作需要独立的显式能力；
- CPU、内存、磁盘、进程数和执行时间有上限；
- 日志和准备写入项目仓库的输出必须隐藏密码、Token 与 Cookie；
- 所有工具行动记录输入、输出、工具版本、超时、重试和幂等信息。

worktree 不是完整安全边界。实际命令和插件调用必须由隔离 Runner/Tool Broker 执行。

## 11. 中央插件与无状态工具系统

Agent Session 不携带完整开发环境。目标枝干 worktree 只保存项目输入、源码、声明文件和有意义的产出；编译器、浏览器、专业软件、依赖缓存和临时构建目录由中央工具系统管理。

### 11.1 插件构成

用户与 Agent 只面对一个统一工具目录，但底层不把所有内容硬塞成同一种包：Rust、Python、GCC、Node 等编译器和库是可按摘要复用的版本化环境资源；“编译 Rust 项目”“运行 Playwright”“生成 PPT”等是可发现、可调用的插件能力。插件可以只提供说明与接口，也可以携带专用 Runtime，并声明自己需要的工具链和依赖资源。

统一插件包可以包含：

- Manifest：名称、版本、摘要、能力、权限、触发条件和资源需求；
- Skill：`SKILL.md` 与按需读取的 references；
- Tools：MCP 兼容的结构化工具接口；
- Runtime：不可变容器镜像、Wasm 组件或其他执行环境；
- Assets：模板、示例和静态资源；
- Tests：插件自检与兼容测试。

C/C++、Python、Rust、Playwright、PPTMaster 以及未来工具都通过同一插件目录发现和调用。插件说明和工具定义不全部注入 Session；Agent 先看到简短目录，选择后再加载 Skill、参数和参考资料。

MCP 用于兼容工具、资源和提示模板的发现与调用；Fudian 额外负责工作区快照、权限、环境版本、资源限制、原子写回与审计。

### 11.2 无状态调用

一次普通工具调用：

1. Session 请求一个带版本的工具操作；
2. Tool Broker 根据枝干快照和环境指纹启动临时 Worker，或复用仍有效且只属于该 Session 的热 Worker；
3. Worker 读取当前 worktree，在独立输出层执行；
4. 返回候选文件变更、Evidence、日志和状态；
5. Broker 验证基线未变化后原子写回允许的结果；
6. Worker 在短期空闲 Lease 内可以继续复用，超时、环境变化或 Session 结束后销毁。

工具接口对 Agent 保持逻辑无状态：每次请求的输入、环境和结果都明确，正确性不能依赖热 Worker 中未声明的修改。热 Worker 只减少启动延迟，不跨 Session 共享可变 home、进程或临时文件，也不成为持久事实来源。

Agent 不得使用 `apt`、裸 `pip install`、`curl | sh` 等方式为自己改变平台工具。项目需要新增库时，Agent 正常修改 `Cargo.toml`、`pyproject.toml`、锁文件等项目依赖声明，中央工具系统据此解析并创建或复用隔离环境；这不等于把依赖安装进 worktree。缺少新的平台能力或插件版本时，才创建中央安装请求。

需要短期持续状态的操作使用显式 `ToolLease`，例如开发服务器、交互式浏览器或调试进程。Lease 有明确 ID、资源限制、过期时间和日志；结束后，选定的长期输出写入项目 worktree 并形成 Git 检查点，其余临时数据按策略清理。

### 11.3 版本与依赖隔离

中央共享工具不等于共享一个可变依赖环境。每个 Session 使用不可变的 `EnvironmentManifest`，至少记录：

- 插件 ID、语义版本和内容摘要；
- 工具链与基础运行环境版本；
- 依赖锁文件及其哈希；
- 目标平台、Feature 和构建参数；
- 网络、资源和环境变量策略；
- 由以上内容计算的环境指纹。

不同 Session 可以同时使用彼此不兼容的库版本。中央存储按内容和环境指纹去重，但环境之间不能共享可变状态。子枝干默认继承父环境；修改依赖会生成新的环境版本，不影响父枝干。

同一版本的编译器、包和不可变层在服务器上按内容只保存一份，各 Session 环境以只读引用或隔离视图复用；可写缓存、构建目录、进程和 home 始终属于单个环境或 Worker。去重是存储优化，不能让一个 Session 的安装、缓存污染或删除影响另一个 Session。

拟合并时必须在干净环境中重新构建和测试，并把依赖与环境差异列入审核。`latest` 只能在首次解析时使用，随后固定具体版本和内容摘要。

## 12. 数据、Git 与项目文件

Fudian 运行时不是一个包住全部项目的“总 Git”或父仓库。每个正式 Project 拥有一个逻辑独立的托管 Git 仓库和项目级 Git LFS 命名空间；该项目的 GoalBranch 都是这个仓库中的 branch。每个项目可以绑定并推送到自己对应的 GitHub 仓库。不同项目可以共用物理存储服务，但不能通过嵌套仓库、submodule 或父级 Git 历史拼成一棵总仓库。

项目可以从一个新的空 Git 仓库开始，也可以在用户授权后从已有 GitHub 仓库的当前默认 branch 开始。Fudian 不强制创建 `.fudian/`、`docs/` 或 `src/` 等产品私有目录；仓库目录由项目自身需要决定。代码、设计文档、研究结论等真实项目成果正常进入仓库，目标图、完整对话、审批状态等 Fudian 内部运行数据留在 PostgreSQL 和完整项目备份中。标准 `.gitignore`、`.gitattributes`、依赖锁文件和项目主动选择的配置仍属于正常项目文件。

- PostgreSQL 保存项目关系、目标枝干、Session、Proposal、事件、审核、队列和引用元数据；
- 所有进入项目工作树、需要随枝干分叉和合并的文件都由 Git 管理；适合直接存放的使用普通 Git，不适合直接存放的大文件使用标准 Git LFS；
- 不按“代码 / 非代码”或“文本 / 二进制”机械分流：小型图片可以直接进入 Git，大型文本数据也可以进入 Git LFS；具体匹配规则写入仓库的 `.gitattributes`；
- Fudian 不设计自定义大文件指针协议。Git LFS 的实际对象可以由自托管 LFS 服务保存在本地文件系统、S3 或 MinIO，但它们仍属于同一套 Git 历史；
- 需要长期保留的证明材料、运行输出和用户输入也必须进入该项目的 Git 或 Git LFS；Evidence 在 PostgreSQL 中保存结构化说明，并引用准确的 commit、路径和内容哈希，不复制文件内容；
- 不设置长期 Artifact 或 EvidenceAttachment 文件仓库。对象存储只作为标准 Git LFS 的物理后端，以及未完成上传、Runner 输出层和缓存的临时空间；临时对象没有项目版本语义，未被选入 worktree 就按策略清理；
- 普通 Git 和 Git LFS 默认都不使用 Fudian 自定义跨枝干文件锁；系统可以提前提示相同路径被多个活动枝干修改，但冲突仍在 Merge Gate 中按标准 Git 语义解决。以后只有出现真实重复浪费时，才对特定路径评估标准 Git LFS lock；
- Session 工作过程可以修改，进入审核的候选现场必须冻结；
- 被拒绝的枝干不污染父枝干，但其 Git ref、项目文件与 Evidence 仍可追溯；
- PostgreSQL、各项目 Git 仓库、Git LFS 对象和环境清单必须能够一致备份、校验、导出和恢复；临时上传和缓存不属于恢复承诺；
- 密钥、Cookie 和其他秘密不能进入项目 Git 历史。

Fudian 自身源码也使用独立 Git 仓库，但它只管理 Fudian 软件的开发和发布，不是用户项目仓库的父仓库。开发采用可运行的主分支、短期功能分支/worktree、可解释的小提交和自动化质量门。项目 GitHub 远程仓库由用户创建和授权绑定，Agent 不擅自发布。

Fudian 内部目标枝干默认只保存在托管仓库；普通远端默认只推送项目默认分支，避免把所有内部执行枝干暴露成远端协作分支。用户可以通过显式导出设置选择同步活动枝干或完整审计 refs。

项目绑定 GitHub 后，凡是经过用户接受并使项目默认 branch 前进的更新，默认自动推送；项目设置可以关闭自动推送并改为手动同步。推送失败不撤销已经接受的本地结果，而是在项目现场显示同步失败、原因和重试入口。未经用户接受的目标枝干、候选和工作中检查点不能因为自动同步而被推送。

第一版的 GitHub 连接采用 Fudian 单写模式：接入已有仓库时冻结并记录当时的远端默认 branch 与 commit，之后只有这一套 Fudian 服务器能够写入该仓库的 branches。用户和 CI 仍可读取、克隆和运行检查，但不在 GitHub 网页、其他电脑、机器人或另一套 Fudian 中直接提交、合并或推送。Fudian 每次推送前都必须先验证远端仍等于最后一次已知状态；发现意外前进、改写或删除时停止推送并通知用户，不自动覆盖或猜测整合。多人或多写入协作不属于第一版。

### 12.1 项目导出与恢复

Fudian 的源码、安装包和容器镜像不携带任何用户运行数据。项目文件推送到 GitHub 只是项目自身的 Git/Git LFS 同步，不是 Fudian 工作状态备份；系统不创建隐藏状态 branch，也不把 Session、对话或审批记录偷偷推送到项目远端。

用户显式执行“导出项目”时，系统生成一个带格式版本、清单和校验值的单文件项目备份。它必须完整包含该项目的全部持久内容：

- 项目 Git 仓库的所有必要 refs、commit 和 Git LFS 对象；
- 目标枝干图、目标说明的全部版本和生命周期状态；
- Session、完整对话、Proposal 的全部版本及决定；
- Evidence、MergeGate、审核、暂停、恢复和事件历史；
- 可复现工作所需的插件版本、环境清单、来源引用和内容摘要；
- 其他属于该项目且无法从以上内容重建的持久记录。

导入该文件必须能够在一套新的 Fudian 实例中恢复完整项目，而不仅是恢复默认 branch 的文件。账号密码、登录会话、API 密钥、GitHub 凭据等秘密不进入项目备份；导入时由当前实例重新授权。缓存、临时上传、运行中的进程和可重新取得的工具二进制也不进入备份，但其必要版本和环境声明必须保留。

项目运行中也可以请求导出。系统先让正在写入的行动到达可恢复的安全检查点，再短暂冻结该项目的写入，从 PostgreSQL、Git 和 Git LFS 取得同一逻辑时刻的一致快照。备份完成并通过清单校验后自动解除冻结，原有 Session 从检查点继续；等待期间和失败原因必须在当前工作现场可见。系统不得导出数据库、Git commit 和 LFS 对象彼此不匹配的半成品。

导入时若当前实例已经存在同一来源项目，默认创建拥有新本地身份的完整副本，并保留原项目身份、备份时间和来源摘要，不覆盖现有项目。用户显式选择替换时，系统必须先把现有项目冻结并生成一份通过校验的自动备份，再请求最终确认并执行可恢复替换；备份或校验失败就不得替换。GitHub 远端绑定和外部凭据始终需要重新确认，不能随导入覆盖。

项目备份默认使用用户在导出时设置的独立备份密码进行完整性保护的加密；密码不写入备份、不进入日志，也不由服务器长期保存，遗失后无法代为恢复。用户仍可显式选择未加密导出，但界面必须在执行前说明完整对话和项目内容会以可直接读取的形式存在。具体密码派生与加密算法属于带格式版本的实现细节，只能采用经过公开审查的标准方案，不能自行设计密码协议。

项目导出是用户主动创建的恢复点，不是持续远端备份承诺。服务器损坏时，未进入有效导出文件或实例级备份的数据可以丢失。

## 13. 文件导入

电脑、手机和平板都能向当前 Agent Session 提供文件。文件实际关联当前 Session，并进入其目标枝干的输入边界。

导入流程：

1. 客户端选择、拖放、粘贴或上传文件；
2. 服务器写入授权的暂存区；
3. 检查文件名、路径、大小、类型、压缩包边界和内容哈希；
4. 登记为待导入上传记录；
5. 默认把文件安全复制到当前枝干 inbox；普通文件进入 Git，符合仓库 LFS 规则的大文件进入标准 Git LFS；
6. 用户明确选择“仅供本次运行”时，文件可以暂时只读提供给 Session，但不能成为拟合并依据；需要继续引用时必须先导入项目 Git/Git LFS；
7. 当前 Session 收到新的输入事件。

系统可以安全保存未知格式，但只有安装了相应插件后才能理解、预览或编辑。等待拟合并的冻结现场不能被上传文件悄悄改变；新文件应成为后续 Session 的输入。

## 14. 后台执行与恢复

网页服务、持久调度和实际工具执行分离。Session 是数据库中的持久对象，不依赖某个长连接或进程一直存活。

- 实际工作拆成带状态的 ActionRun；
- 每项行动在执行前登记，完成后记录结果；
- Worker 使用租约和心跳；
- 服务重启后识别未完成行动并安全恢复；
- 只有已知可安全重试的行动才有限次数重试；
- 不明确的外部副作用不能盲目重放；
- 用户可以暂停、继续或取消；
- 外部条件未满足时进入等待并记录恢复条件，不进行忙循环；
- 早晨摘要列出成果、失败、开放枝干与待处理决定。

暂停通知必须包含原因、最后安全检查点、已经尝试的办法、风险、需要用户做什么和建议处理方式。来源对象的等待状态始终存在；站内“待我处理”由这些状态生成，站外通知通过可替换适配器发送并去重。通知投递记录只证明是否发送、送达或已读，不拥有暂停与恢复状态。

## 15. 测试、证据与审核

目标说明可以包含机器可验证标准、人工判断标准和探索问题。执行 Agent 只有在认为整条枝干目标满足时才能拟合并。

拟合并至少经过：

1. 工作 Agent 对目标、依赖、假设和遗漏项自查；
2. 执行可以客观运行的构建、测试、浏览器验证或资料核验；
3. 独立审核 AI 在冻结现场上检查证据、寻找反例并重新运行必要测试；
4. 用户查看结论、差异、项目文件、Evidence 和审核意见后最终决定。

可以机器验证的内容不能只写“AI 认为通过”。测试结果必须关联准确的 Git commit、相关文件路径与内容哈希、插件版本和环境指纹。

子枝干通过不等于父目标自动通过；父 Session 必须对回流结果做整合验证。所有已发现的必需子目标必须得到接受、明确失败或经用户有理由地豁免，父目标才能进入候选完成。

## 16. 前端交互基线

项目界面不是普通仪表盘或聊天首页，而是一种 Git 图与 VS Code 工作台混合的项目操作空间。

用户像老板一样在两个视角之间移动：

- **管理视角**：查看目标枝干、Agent Session、运行状态、子目标、暂停、拟合并和待处理事项；
- **工作现场**：点击 Session 节点，进入它操作文件、编辑代码、使用浏览器、运行软件、执行测试和形成成果的现场。

视觉继续继承老 Fudian 的纸张感、黑白主色、酸绿色强调、固定导航、紧凑和克制的工具感。避免让通用聊天框、SaaS 卡片和视觉噪音成为产品中心。

项目图的稳定语义是：

- 枝干代表目标；
- 主要节点代表 Agent Session；
- 拟分支、请求判断、拟合并、审核、恢复和实际合并都是完整事件。

拟合并与实际整合固定显示为枝干回流处的菱形 Merge Gate；其内部准备、冲突处理、测试、独立审核和用户决定阶段在详情中展开。其他暂停、请求判断和恢复事件最终显示成主要节点、边上标记还是详情卡片仍不锁定。底层完整记录，渲染方式通过可替换的图投影决定。

桌面端提供完整工作台；手机和平板可以在原对话中查看、讨论和接受 Proposal、查看状态、处理暂停、审核拟合并、上传文件并推进项目。Proposal 卡片可以采用对话内嵌、输入区上方固定或移动端底部弹层，但不能通过整页跳转切断原对话。具体面板位置、图所占空间和工作台切换方式留给可操作原型验证。

## 17. 部署与访问

第一阶段正式形态是部署在中等性能服务器上的响应式 Web/PWA：

- Docker Compose 负责可重复部署；
- Rust Web Server 负责产品页面、API、审核和持久状态；
- PostgreSQL、各项目 Git 仓库与 Git LFS 对象使用持久存储；
- Rust Runner/Tool Broker 负责中央插件、临时 Worker 和 Lease；
- 通过并发上限和持久队列适配服务器资源；
- 远程访问必须使用身份认证和 HTTPS；
- 可以先通过私人网络访问，公开域名部署需要受控反向代理；
- 桌面原生壳不是第一阶段依赖，交互稳定后再评估；
- 更新前备份，迁移可追踪，工具和数据版本可恢复。

## 18. 不可违反的产品不变量

1. 用户不负责填写巨量结构化表格，AI 负责整理 Proposal。
2. 未知必须诚实标记，不用虚假精确掩盖不确定性。
3. 目标是一条枝干，Agent Session 是枝干上的主要节点。
4. 同一目标枝干同一时间只有一个可写 Agent；并行必须先拆子目标枝干。
5. 未经批准的 BranchProposal 不会启动正式子枝干。
6. 接受 ProjectProposal 会直接启动项目与根 Session，不再二次批准根目标。
7. 拟合并只表示工作 Agent 声称整条枝干目标已达成。
8. 未经用户接受，任何拟合并都不能影响父枝干。
9. AI 可以提出根项目候选完成，只有用户可以最终确认完成。
10. Session 范围内自主执行，跨枝干变化通过审核边界发生。
11. Session 不自行安装工具；工具由中央版本化插件系统提供。
12. 不同 Session 的依赖环境必须隔离、固定并可复现。
13. 上下文、工具和界面都遵循按需披露、渐进式披露。
14. 所有重要结论、文件变化、审核和合并都必须可追溯。
15. 暂停必须让来源对象进入等待用户状态，并主动通知用户。
16. 视觉原型可以迭代，底层语义不能因某次布局草案而被绑死。

## 19. 当前明确不锁定的事项

- 想法一级空间的具体工作流；
- 图与工作台的最终布局；
- 暂停、请求判断和恢复事件是否显示为主要节点；
- 首个正式 AI Provider 及模型组合；
- 插件仓库、签名、安装审批与发布格式的最终细节；
- 私人网络、公网域名和身份认证的最终部署组合；
- 站外通知的首个具体渠道；
- 日志、缓存和废弃 worktree 的最终保留策略；
- 桌面壳是否需要以及采用何种技术。
- Agent Session 是否采用 Agent Team，以及 Team 内并行写代码、文档和整合工作区的具体模型；
- 尚未审核的跨枝干临时信息是否需要点对点 Signal、由谁判断关联，以及是否存在项目级 Coordinator Agent。

这些事项可以通过后续 Goal、原型和使用反馈逐项形成新的决策，但不得阻塞已经明确的领域骨架实现。

Agent Team 与未审核跨枝干通信在 2026-08-24 的讨论中被用户明确搁置。当前实现不得预设固定 Team 角色、隐藏的内部任务树、临时 Signal 或全局 Coordinator；只有用户以后主动重开该议题时才能继续设计。已经审核并 merge 的父枝干更新通知属于已接受的 Git 状态同步规则，不在本次搁置范围内。

## 20. 第一阶段实现原则

第一阶段优先实现难以返工的领域模型、事件语义、状态机、版本边界和纵向验证流程。界面只需要证明真实工作流能够跑通，不应在用户尚未体验前过早锁定最终布局。

当前仍是正式测试前的设计与开发期，现有数据库、项目和对话均视为可丢弃的开发样本，不承担保留、读取或转换义务。必须先逐项确定并由用户接受核心对象、身份、关系、状态、权限和持久化边界，再一次性删除被否定的 Artifact、GoalContract、Contribution、AttentionItem 等结构及兼容代码，以干净数据库和存储重新建立第一版基线。只有目标模型、初始 schema/API 和关键纵向测试一起通过用户审查后，才进入正式测试。

从正式测试基线开始，持久数据才成为必须保护的数据。此后的结构演进必须使用可验证的前向迁移、变更前备份和回退方案，不能再以清库代替迁移。“测试前定死”指核心产品语义达到可承诺基线，不代表软件以后永远不能增加字段或修复设计。

任何第一阶段 Goal 都必须：

- 明确引用本文件；
- 列出本阶段覆盖与不覆盖的章节；
- 使用隔离数据库和临时运行环境验证全新建库、升级边界和关键流程；
- 只在已确认的开发环境中重置数据，不能把不确定目标当作可丢弃数据；
- 不擅自公开部署、推送 GitHub 或使用私人凭据；
- 在结束时报告已完成内容、验证证据、仍未解决事项和下一步建议。
