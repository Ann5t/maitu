# Fudian 产品设计基线

- 文档版本：0.2
- 基线日期：2026-08-22
- 状态：讨论中；2026-08-23 之后的目标图、Git/LFS 与工具系统讨论尚未完整回填
- 适用范围：Fudian 第一版及其后续 Goal、实现、测试与评审

## 1. 文档用途

这份文件记录 Fudian 的长期产品约束，不是某一次开发任务的待办清单。

后续每个实现 Goal 都必须引用本文件。Goal 可以选择本阶段要实现的子集，但不得在没有记录新决策的情况下悄悄改变这里已经确定的语义。新的讨论可以修订本文件；旧结论应保留在版本历史中，而不是只存在于聊天记录里。

当前工程就是 Fudian 的第一版。遗失工程、历史 Docker 镜像、数据库名称和界面资料只作为取证、数据兼容与设计参考，不构成产品前代，也不在产品界面中形成“桌面版 / Docker 版 / Rust 版 / nextgen”等版本叙事。`Rust` 只描述技术栈；内部 schema、协议或 BranchProposal 的 `v0.1` 等编号也不等于产品版本。

[`architecture/architecture.md`](../architecture/architecture.md) 描述当前已经实现的技术状态；本文件描述要建设的产品。两者不应混为一谈。

## 2. 一句话定义

Fudian 是一个单用户、自托管、面向长期目标推进的项目执行系统：用户提出意图，AI 与用户逐步形成目标，多个 Agent 通过目标枝干进行探索和产出，所有结果带着证据与来源回流，最终由用户决定是否接受、合并和完成。

它不是通用笔记软件、普通任务清单或以聊天框为中心的 AI 助手。

## 3. 顶层信息架构

产品存在两个一级空间：

- **想法**：项目的上游，用来收集、发展和筛选尚未形成项目的意图。
- **项目**：目标开始被正式推进后的运行空间。

想法空间的具体设计延后。第一阶段先把项目空间设计正确，想法的设计以后服务于从意图到项目的转化。

## 4. 已确定的核心术语

### 4.1 Project

项目是稳定的身份、总目标和生命周期容器。项目包含一条根目标枝干以及由它递归展开的子目标枝干。

### 4.2 GoalBranch

**一个目标对应一整条枝干。**

目标枝干持有：

- 当前版本的目标契约；
- 从父枝干继承的上下文与产物引用；
- 唯一且持续存在的 Git branch，以及需要时挂载的 worktree；
- 依次发生的 Agent Session 节点；
- 子目标枝干、回流成果与审核记录；
- 当前状态和未解决条件。

一个正式 GoalBranch 严格对应一个 Git branch。根 GoalBranch 直接使用项目默认分支；子 GoalBranch 在 Proposal 获批后，从父 Session 的准确安全 commit 创建。BranchProposal 本身没有 branch 或可写 worktree。

Git branch 是长期身份，物理 worktree 只是可重建的运行现场：活动时挂载，暂停或归档后可以释放，需要时从已记录并现场核验的 commit 重建。同一目标枝干同一时间只允许一个 Agent 修改其 worktree。需要并行时，必须先提出并批准新的子目标枝干。

运行中的 GoalBranch 必须位于目标树的执行前沿：一条枝干只要存在运行中的后代目标，就不能同时运行自己的工作 Agent。父 Session 在子枝干开始前形成安全 commit、释放写租约并进入等待；并行工作由兄弟子枝干表达。父目标尚未完成的主线若要并行继续，也应形成边界明确的子目标，而不是由父 Agent 一边协调一边修改文件。

父枝干等待期间可以由受控整合流程接收已经审核通过的子枝干 merge，因此其 Git HEAD 可能前进，但这不等于父工作 Agent 正在执行。只有必需子目标均已接受、明确失败或被用户有理由地豁免，且没有运行中的后代后，父枝干才能创建下一 Session 恢复整合和推进。

GoalBranch 进入 `integrated | stopped | archived` 等终态后，其 Git ref 保留并由 Fudian 设为只读，继续指向最终 HEAD；物理 worktree 在确认没有活动租约或整合任务后释放。Git 和 Git LFS 对象继续可达，因此现场可以按原 commit 与环境记录重建。若以后要从旧成果继续，创建来源清楚的新 GoalBranch，不重新激活已经结束的枝干。

### 4.3 AgentSessionNode

**一个 Agent Session 是目标枝干上的主要节点。**

Session 内部可以包含大量行动、小目标、命令、测试、浏览器操作和轻量检查点；这些内容进入 Session 的详情与事件记录，不自动成为项目主图上的主要节点。

一个执行进程崩溃后恢复，仍属于同一个 Session 节点。只有审核退回后开始新一轮工作，或明确重新分配一轮工作时，才在同一枝干上创建下一个 Session 节点。

同一 GoalBranch 上的 Session 连续接力。后一个 Session 必须从前一个 Session 的最终安全 commit 开始，不回到父枝干或初始基线；Session 切换不创建 branch，也不发生 merge。前一个 Session 的有意义文件变化必须在交接前形成干净的检查点 commit，不能依赖某个未提交的物理目录继续存在。

审核退回后的新 Session 默认继承被冻结候选的完整状态，再根据反馈继续修改。需要放弃旧变化时，以新的修改或 revert 保留历史，不通过重写历史假装旧工作没有发生。一个 Session 可以产生零到多个 commit；Session 和 commit 不是同一种节点。

### 4.4 BranchProposal

创建目标枝干前统一使用 `BranchProposal`，不强制存在“第零号节点”。

BranchProposal 记录：

- 为什么需要这条枝干；
- 目标契约草稿；
- 已知约束和未知问题；
- 期望返回父枝干的贡献；
- 探索与停止方式；
- 需要用户判断的时机；
- 上下文继承点和工具需求。

BranchProposal 可以附着在父 Session 上简洁展示，也可以打开独立的完整讨论界面，但始终只是同一个 BranchProposal，不因此变成 Agent Session 节点。用户批准前不启动执行 Agent，也不创建正式可写 worktree。

### 4.5 Contribution、Artifact、Evidence

- `Contribution`：准备回流的结论、发现、决定、条件、代码变化或其他有意义成果。
- `Artifact`：文件、图片、报告、数据集、代码提交、浏览器 Trace 等可固定版本的产物。
- `Evidence`：支持、反驳或阻塞目标判断的观察与测试结果。

Contribution 用于说明枝干带回了什么、由什么证据支持，不作为挑选 Git 提交的第二套合并单位。子枝干只有在整体可接受时，才通过标准 Git merge 回到直接父枝干。

## 5. 项目执行循环

### 5.1 从意图到执行

1. 用户用自然语言表达想做的事，可以只是一句话。
2. AI 根据父枝干上下文整理 BranchProposal 和目标契约草稿。
3. AI 只询问会实质改变方向、权限或可执行性的关键问题。
4. 用户批准 Proposal。
5. 系统从准确的父节点快照创建目标枝干、worktree 和第一个 Agent Session。
6. Session 在自身边界内自主推进。

### 5.2 Session 的正常出口

Agent 没有达成枝干目标时：

- 如果仍能自行推进，就继续当前 Session；
- 如果目标太大或需要并行，就提出拟分支并暂停；
- 如果需要用户的品味、科研判断或方向选择，就请求判断；
- 如果缺少外部条件或无法安全继续，就异常暂停。

只有当工作 Agent 认为**整条目标枝干的目标已经达成**时，才能提出拟合并。拟合并不是阶段汇报，也不是已经发生的合并。

子枝干发现更多工作时，属于自身目标范围的继续向下拆分；实际属于祖先目标范围的，通过待处理事项向正确祖先提出新的兄弟 BranchProposal。创建和审批 Proposal 不要求重新启动祖先工作 Agent。

### 5.3 拟合并与退回

拟合并时冻结候选现场，包括准确的 Git 状态、产物、证据、环境版本和测试结果。

- 独立审核 AI 检查候选结果；
- 用户最终决定接受、提出部分接受意见并退回整理、退回或放弃；
- 未经用户接受，候选结果不得影响父枝干；
- 退回后，根据用户与 AI 的讨论在同一目标枝干创建下一个 Session 节点继续；
- 部分接受只记录已认可内容和仍需修改的反馈，不执行物理合并；Agent 先在原枝干继续整理，或在合并前提出新的子目标进行拆分；
- 整体接受后，系统只使用 `git merge --no-ff` 把完整子枝干合入直接父枝干；不在审批阶段 cherry-pick、拼补丁或另造文件合并协议；
- Contribution、Evidence 和审核记录随整枝合并结果建立来源关系，父 Session 随后恢复或开始新的整合 Session。

合并先在隔离的整合 worktree 中形成候选并重新验证。Git 冲突按 Git 的正常冲突语义处理；Fudian 负责暂停、展示冲突、安排整合 Session 和保存审核记录，不自行发明另一套冲突算法。Git 是文件内容、提交历史、diff 与 merge 结果的权威来源；PostgreSQL 只保存领域状态、Git 引用及冻结对象 ID 作为映射和证据。

拟合并边界使用一个可见的菱形 Merge Gate。系统从父枝干当前安全 HEAD 建立隔离整合 worktree，对冻结子枝干执行标准 `git merge --no-ff`。没有 Git 冲突也必须重新构建和测试；发生冲突时，由有写权的 Integration Agent 只在隔离候选中完成三方合并，再交给另一个只读的独立 Review AI 复核。用户批准最终候选后，系统才以 compare-and-swap 更新父 branch。

普通 Git 与 Git LFS 经过同一 Merge Gate。文本由 Agent 结合 base、父版本和子版本处理；只有存在相应格式插件时，Agent 才能尝试二进制语义合并。无法理解或自动融合的文件必须明确给出保留父版本、保留子版本、两份并存或人工重制等选择，不能伪造成功。若冲突处理已经成为独立的大目标，则撤回候选，回原子枝干创建新 Session 或继续拆分。

多个兄弟子枝干只在没有已知前置依赖时并行。任一子枝干通过审核并被用户接受后立即 merge 到直接父枝干，不等待其他兄弟完成。仍在运行的兄弟保持原创建基线，不被系统自动 rebase、reset 或 merge；父枝干的推进由受控整合流程完成，不启动父工作 Agent。父更新怎样通知和同步给其他枝干由独立规则约束。

根目标没有父枝干，因此对应的是“候选完成”。AI 可以提出候选完成，只有用户可以最终确认项目完成。

### 5.4 暂停类型

用户界面必须区分：

- **等待拟分支审查**：Agent 认为需要拆出新的目标枝干；
- **等待判断**：当前目标需要用户的直觉、品味或科研判断；
- **等待拟合并审查**：Agent 声称枝干目标已经达成；
- **异常暂停**：工具失败、缺少条件、预算耗尽或无法安全继续；
- **手动暂停**：用户主动停止当前执行。

暂停后必须产生持久的待处理事项并主动通知用户，不能只写日志。

## 6. 成果与完成语义

每个项目和目标枝干都有版本化目标契约。契约可以同时包含：

- 想达到的外部结果；
- 明确的硬约束；
- 主观偏好；
- 当前未知问题；
- 不做什么；
- 验证或探索方法；
- 何时请求用户判断；
- 停止条件与回流方式。

状态语义严格区分：

- **完成**：证据满足当前目标契约，且用户最终确认；
- **停止**：用户明确放弃继续推进，原因和已有成果保留；
- **等待**：缺少外部条件，并记录恢复条件；
- **归档**：只是一种存储与展示状态，不代表成功或失败；
- **枝干失败**：不等于项目失败，负面结论也可能是有效贡献。

AI 无权自行确认根项目完成。

## 7. 最低充分明确度

结构化是系统的负担，不是用户的填表任务。

用户默认通过自然语言、文件、图片或语音表达意图。AI 负责生成结构化 Proposal；用户只审核简短的目标方向、关键边界、重要推断和需要判断的事项。详细字段按需展开。

目标契约不追求虚假的“全部明确”，而追求最低充分明确度：

- 已知且稳定的部分明确记录；
- AI 推断的部分标注为推断；
- 不知道的部分诚实标注为未知；
- 低风险未知可以通过探索逐步收敛；
- 会实质改变范围或方向的问题必须找用户；
- 执行 Agent 不能自行降低或偷偷修改目标契约，只能提出版本修订。

用户在使用过程中的灵感和感受可以持续形成契约修订建议。只有用户确认后，它们才成为正式的新版本。

## 8. 探索型与主观型目标

设计和科研目标可能无法在开始前定义最终效果。此时目标契约应定义探索过程，而不是伪造结果标准：

- 当前意图和方向；
- 已知硬边界；
- 尚未确定的问题；
- 要制作的原型、实验或候选方案；
- 预算和停止条件；
- 何时请求用户体验或判断；
- 谁拥有最终判断权。

一次探索即使否定了原假设，也可能成功完成目标，因为它减少了不确定性。系统可以保证所有已经发现的依赖、假设和未解决项不会被悄悄遗漏，但不能声称已经排除科研中的所有未知未知。

## 9. 上下文与记忆

每条子枝干继承父节点的全部可用产物和上下文，但不把全部历史同时塞入模型窗口。

上下文采用按需披露、渐进式披露：

1. 默认提供目标契约、权限边界、当前状态和当前节点；
2. 提供继承的决策、产物和证据目录；
3. 根据当前工作加载相关摘要与片段；
4. Agent 需要验证细节时读取完整原文、文件和日志。

目标、硬约束和权限边界永远不会被折叠。摘要、全文索引和向量索引都是可重建的辅助层，不是权威事实来源。

重要结论必须写成带来源的结构化记录，并能追溯到节点、证据、产物或外部资料。外部网页始终是不可信资料，不能成为系统指令。

子枝干获批并合入父枝干后，系统向仍基于旧父 commit 运行的直接子枝干提供轻量父更新通知。通知由真实 merge commit、Contribution 和 Evidence 推导，只默认披露来源目标、摘要、改变路径和证据目录；完整 diff、文件和证据按需读取。数据库只记录通知的投递、读取和处理状态，不复制另一套成果历史。

接收 Agent 可以忽略与目标无关的更新，或在安全 commit 后显式把父枝干 merge 到自己的枝干。系统不得自动 rebase、reset 或修改接收方 worktree。检测到修改路径重叠时，接收方在下一个安全点先评估；实际冲突进入明确的冲突处理流程。

## 10. 自主权限与安全边界

Session 在批准的目标枝干内自主执行，不逐次请求用户许可。跨枝干影响只能通过 Proposal、审核与真正合并发生。

工作区与执行安全遵循：

- 父级快照只读，当前目标枝干可写；
- 不允许读取或修改其他枝干；
- 不暴露宿主机用户目录、SSH 密钥、私人浏览器资料或容器运行时 Socket；
- 公共互联网可以用于搜索和浏览；
- 登录私人账号、发送消息、部署、付费和其他外部写操作需要独立的显式能力；
- CPU、内存、磁盘、进程数和执行时间有上限；
- 日志和产物需要隐藏密码、Token 与 Cookie；
- 所有工具行动记录输入、输出、工具版本、超时、重试和幂等信息。

worktree 不是完整安全边界。实际命令和插件调用必须由隔离 Runner/Tool Broker 执行。

## 11. 中央插件与无状态工具系统

Agent Session 不携带完整开发环境。目标枝干 worktree 只保存项目输入、源码、声明文件和有意义的产出；编译器、浏览器、专业软件、依赖缓存和临时构建目录由中央工具系统管理。

### 11.1 插件构成

统一插件包可以包含：

- Manifest：名称、版本、摘要、能力、权限、触发条件和资源需求；
- Skill：`SKILL.md` 与按需读取的 references；
- Tools：MCP 兼容的结构化工具接口；
- Runtime：不可变容器镜像、Wasm 组件或其他执行环境；
- Assets：模板、示例和静态资源；
- Tests：插件自检与兼容测试。

C/C++、Python、Rust、Playwright、PPTMaster 以及未来工具都通过同一插件目录发现和调用。插件说明和工具定义不全部注入 Session；Agent 先看到简短目录，选择后再加载 Skill、参数和参考资料。

MCP 用于兼容工具、资源和提示模板的发现与调用；Fudian 额外负责工作区快照、权限、环境版本、资源限制、原子写回与审计。

### 11.2 无状态调用

一次普通工具调用：

1. Session 请求一个带版本的工具操作；
2. Tool Broker 根据枝干快照和环境指纹启动临时 Worker；
3. Worker 读取当前 worktree，在独立输出层执行；
4. 返回变更集、产物、证据、日志和状态；
5. Broker 验证基线未变化后原子写回允许的结果；
6. 临时 Worker 销毁。

Agent 不得使用 `apt`、`pip install`、`curl` 等方式为自己安装工具。缺少能力或工具版本时，创建中央安装请求。

需要短期持续状态的操作使用显式 `ToolLease`，例如开发服务器、交互式浏览器或调试进程。Lease 有明确 ID、资源限制、过期时间和日志；结束后只保留选定产物。

### 11.3 版本与依赖隔离

中央共享工具不等于共享一个可变依赖环境。每个 Session 使用不可变的 `EnvironmentManifest`，至少记录：

- 插件 ID、语义版本和内容摘要；
- 工具链与基础运行环境版本；
- 依赖锁文件及其哈希；
- 目标平台、Feature 和构建参数；
- 网络、资源和环境变量策略；
- 由以上内容计算的环境指纹。

不同 Session 可以同时使用彼此不兼容的库版本。中央存储按内容和环境指纹去重，但环境之间不能共享可变状态。子枝干默认继承父环境；修改依赖会生成新的环境版本，不影响父枝干。

拟合并时必须在干净环境中重新构建和测试，并把依赖与环境差异列入审核。`latest` 只能在首次解析时使用，随后固定具体版本和内容摘要。

## 12. 数据、Git 与产物

- PostgreSQL 保存项目关系、目标枝干、Session、Proposal、事件、审核、队列和引用元数据；
- 所有进入项目工作树、需要随枝干分叉和合并的文件都由 Git 管理；适合直接存放的使用普通 Git，不适合直接存放的大文件使用标准 Git LFS；
- 不按“代码 / 非代码”或“文本 / 二进制”机械分流：小型图片可以直接进入 Git，大型文本数据也可以进入 Git LFS；具体匹配规则写入仓库的 `.gitattributes`；
- Fudian 不设计自定义大文件指针协议。Git LFS 的实际对象可以由自托管 LFS 服务保存在本地文件系统、S3 或 MinIO，但它们仍属于同一套 Git 历史；
- Artifact 仓库只保存不属于项目工作树的不可变证据、运行输出和临时上传对象，不作为另一套项目文件版本历史；
- 普通 Git 和 Git LFS 默认都不使用 Fudian 自定义跨枝干文件锁；系统可以提前提示相同路径被多个活动枝干修改，但冲突仍在 Merge Gate 中按标准 Git 语义解决。以后只有出现真实重复浪费时，才对特定路径评估标准 Git LFS lock；
- 一个逻辑产物可以有多个不可变版本；
- Session 工作过程可以修改，进入审核的候选现场必须冻结；
- 每个产物记录来源枝干、Session、工具调用、内容哈希和父版本；
- 被拒绝的枝干不污染父枝干，但其历史和产物仍可追溯；
- 数据库、Git、产物与环境清单可以整体备份、校验、导出和恢复；
- 密钥、Cookie 和其他秘密不能进入普通产物仓库。

Fudian 自身源码也必须进入独立 Git 仓库。开发采用可运行的主分支、短期功能分支/worktree、可解释的小提交和自动化质量门。GitHub 远程仓库由用户创建和上传，Agent 不擅自发布。

Fudian 内部目标枝干默认只保存在托管仓库；普通远端默认只推送项目默认分支，避免把所有内部执行枝干暴露成远端协作分支。用户可以通过显式导出设置选择同步活动枝干或完整审计 refs。

## 13. 文件导入

电脑、手机和平板都能向当前 Agent Session 提供文件。文件实际关联当前 Session，并进入其目标枝干的输入边界。

导入流程：

1. 客户端选择、拖放、粘贴或上传文件；
2. 服务器写入授权的暂存区；
3. 检查文件名、路径、大小、类型、压缩包边界和内容哈希；
4. 登记为 `InputArtifact`；
5. 默认把文件安全复制到当前枝干 inbox；普通文件进入 Git，符合仓库 LFS 规则的大文件进入标准 Git LFS；
6. 只有用户明确选择“仅作参考”，或文件只是证据、运行输出和临时对象时，才保留为不进入工作树的 Artifact；
7. 当前 Session 收到新的输入事件。

系统可以安全保存未知格式，但只有安装了相应插件后才能理解、预览或编辑。等待拟合并的冻结现场不能被上传文件悄悄改变；新文件应成为后续 Session 的输入。

## 14. 后台执行与恢复

网页服务、持久调度和实际工具执行分离。Session 是数据库中的持久对象，不依赖某个长连接或进程一直存活。

- 实际工作拆成带状态的 ActionRun；
- 每项行动在执行前登记，完成后记录结果；
- Worker 使用租约和心跳；
- 服务重启后识别未完成行动并安全恢复；
- 只有已知可安全重试的行动才有限次数重试；
- 不明确的外部副作用不能盲目重放；
- 用户可以暂停、继续或取消；
- 外部条件未满足时进入等待并记录恢复条件，不进行忙循环；
- 早晨摘要列出成果、失败、开放枝干与待处理决定。

暂停通知必须包含原因、最后安全检查点、已经尝试的办法、风险、需要用户做什么和建议处理方式。站内待处理记录始终存在，站外通知通过可替换适配器发送并去重。

## 15. 测试、证据与审核

目标契约可以包含机器可验证标准、人工判断标准和探索问题。执行 Agent 只有在认为整条枝干目标满足时才能拟合并。

拟合并至少经过：

1. 工作 Agent 对目标、依赖、假设和遗漏项自查；
2. 执行可以客观运行的构建、测试、浏览器验证或资料核验；
3. 独立审核 AI 在冻结现场上检查证据、寻找反例并重新运行必要测试；
4. 用户查看结论、差异、产物、证据和审核意见后最终决定。

可以机器验证的内容不能只写“AI 认为通过”。测试结果必须关联准确的 Git commit、产物版本、插件版本和环境指纹。

子枝干通过不等于父目标自动通过；父 Session 必须对回流结果做整合验证。所有已发现的必需子目标必须得到接受、明确失败或经用户有理由地豁免，父目标才能进入候选完成。

## 16. 前端交互基线

项目界面不是普通仪表盘或聊天首页，而是一种 Git 图与 VS Code 工作台混合的项目操作空间。

用户像老板一样在两个视角之间移动：

- **管理视角**：查看目标枝干、Agent Session、运行状态、子目标、暂停、拟合并和待处理事项；
- **工作现场**：点击 Session 节点，进入它操作文件、编辑代码、使用浏览器、运行软件、执行测试和形成产物的现场。

视觉继续继承老 Fudian 的纸张感、黑白主色、酸绿色强调、固定导航、紧凑和克制的工具感。避免让通用聊天框、SaaS 卡片和视觉噪音成为产品中心。

项目图的稳定语义是：

- 枝干代表目标；
- 主要节点代表 Agent Session；
- 拟分支、请求判断、拟合并、审核、恢复和实际合并都是完整事件。

拟合并与实际整合固定显示为枝干回流处的菱形 Merge Gate；其内部准备、冲突处理、测试、独立审核和用户决定阶段在详情中展开。其他暂停、请求判断和恢复事件最终显示成主要节点、边上标记还是详情卡片仍不锁定。底层完整记录，渲染方式通过可替换的图投影决定。

桌面端提供完整工作台；手机和平板可以创建和讨论 Proposal、查看状态、处理暂停、审核拟合并、上传文件并推进项目。具体面板位置、图所占空间和工作台切换方式留给可操作原型验证。

## 17. 部署与访问

第一阶段正式形态是部署在中等性能服务器上的响应式 Web/PWA：

- Docker Compose 负责可重复部署；
- Rust Web Server 负责产品页面、API、审核和持久状态；
- PostgreSQL、Git 与产物仓库使用持久存储；
- Rust Runner/Tool Broker 负责中央插件、临时 Worker 和 Lease；
- 通过并发上限和持久队列适配服务器资源；
- 远程访问必须使用身份认证和 HTTPS；
- 可以先通过私人网络访问，公开域名部署需要受控反向代理；
- 桌面原生壳不是第一阶段依赖，交互稳定后再评估；
- 更新前备份，迁移可追踪，工具和数据版本可恢复。

## 18. 不可违反的产品不变量

1. 用户不负责填写巨量结构化表格，AI 负责整理 Proposal。
2. 未知必须诚实标记，不用虚假精确掩盖不确定性。
3. 目标是一条枝干，Agent Session 是枝干上的主要节点。
4. 同一目标枝干同一时间只有一个可写 Agent；并行必须先拆子目标枝干。
5. 未经批准的 BranchProposal 不会启动正式子枝干。
6. 拟合并只表示工作 Agent 声称整条枝干目标已达成。
7. 未经用户接受，任何拟合并都不能影响父枝干。
8. AI 可以提出根项目候选完成，只有用户可以最终确认完成。
9. Session 范围内自主执行，跨枝干变化通过审核边界发生。
10. Session 不自行安装工具；工具由中央版本化插件系统提供。
11. 不同 Session 的依赖环境必须隔离、固定并可复现。
12. 上下文、工具和界面都遵循按需披露、渐进式披露。
13. 所有重要结论、文件变化、审核和合并都必须可追溯。
14. 暂停必须进入待处理并主动通知用户。
15. 视觉原型可以迭代，底层语义不能因某次布局草案而被绑死。

## 19. 当前明确不锁定的事项

- 想法一级空间的具体工作流；
- 图与工作台的最终布局；
- 暂停、请求判断和恢复事件是否显示为主要节点；
- 首个正式 AI Provider 及模型组合；
- 插件仓库、签名、安装审批与发布格式的最终细节；
- 私人网络、公网域名和身份认证的最终部署组合；
- 站外通知的首个具体渠道；
- 日志、缓存和废弃 worktree 的最终保留策略；
- 桌面壳是否需要以及采用何种技术。
- Agent Session 是否采用 Agent Team，以及 Team 内并行写代码、文档和整合工作区的具体模型；
- 尚未审核的跨枝干临时信息是否需要点对点 Signal、由谁判断关联，以及是否存在项目级 Coordinator Agent。

这些事项可以通过后续 Goal、原型和使用反馈逐项形成新的决策，但不得阻塞已经明确的领域骨架实现。

Agent Team 与未审核跨枝干通信在 2026-08-24 的讨论中被用户明确搁置。当前实现不得预设固定 Team 角色、隐藏的内部任务树、临时 Signal 或全局 Coordinator；只有用户以后主动重开该议题时才能继续设计。已经审核并 merge 的父枝干更新通知属于已接受的 Git 状态同步规则，不在本次搁置范围内。

## 20. 第一阶段实现原则

第一阶段优先实现难以返工的领域模型、事件语义、状态机、版本边界和纵向验证流程。界面只需要证明真实工作流能够跑通，不应在用户尚未体验前过早锁定最终布局。

任何第一阶段 Goal 都必须：

- 明确引用本文件；
- 列出本阶段覆盖与不覆盖的章节；
- 使用隔离数据库和临时运行环境验证迁移；
- 不破坏当前真实数据与可恢复备份；
- 不擅自公开部署、推送 GitHub 或使用私人凭据；
- 在结束时报告已完成内容、验证证据、仍未解决事项和下一步建议。
