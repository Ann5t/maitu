# 0022：MergeGate 简要展示自动证据并允许用户例外接受

- 状态：Accepted
- 日期：2026-08-24
- 置信度：高

## 背景

MergeGate 必须给用户足够信息判断枝干是否可以回流，但把测试日志、截图、diff、工具版本和 Evidence 全部铺在页面上会形成难以阅读的清单。让用户或 Agent 手填 Evidence 表也会重复已经由工具和 Runner 知道的事实。

另一个边界是：AI 可能认为某项质量标准尚未完全满足，而用户看过实际效果后仍认为可以接受；这与候选内容本身已经变化、缺失或无法确认不是同一种问题。

## 备选方案

- Gate 默认展示全部日志和结构化字段，并要求人工补齐 Evidence。
- 只给一段 AI 总结，不保留可核验来源。
- Gate 首层显示简短判断，证据自动采集并按需展开。
- 任何验收项不通过都禁止用户接受。
- 用户可以忽略包括候选身份错误在内的所有阻断。

## 决定

MergeGate 的默认审核卡只显示四组信息：改了什么、验证通过什么、仍有什么问题、需要用户判断什么。完整 diff、命令、日志、截图、浏览器 Trace、环境、Evidence 和审核推理从对应条目按需展开。

工具执行、测试、浏览器操作和 Git 操作自动产生 Evidence，至少绑定准确动作、结果、时间、候选 commit、环境和内容引用。用户和 Agent 不填写独立 Evidence 表；人工观察和主观意见通过原对话记录，由系统结构化并保留原始来源。长期证明文件仍进入项目 Git/Git LFS。

用户拥有目标质量的最终判断权。目标说明中的普通条件未满足、未验证，或者 AI 对主观效果评价较低时，Gate 明确显示这些例外，用户仍可以决定整体接受；系统保存用户原始决定、当时警告和被例外接受的条目，不增加强制原因表单。

只有会使“用户究竟在接受什么”无法确定的系统完整性错误才阻止接受，例如候选对象与审核对象不一致、冻结 commit 已变化、必要 Git/LFS 对象缺失、父 HEAD 失效后尚未重新整合，或当前操作者无权决定。这些问题不能通过质量例外绕过，必须先重新建立准确候选。

## 影响

- 用户首先看到短而可判断的信息，需要时仍能追到原始证据。
- Evidence 采集成为工具和运行基础设施的职责，不给用户制造表格工作。
- AI 负责揭示风险但不能替代用户的品味和最终取舍。
- 系统只在决定对象无法确定时阻止接受，不把一般测试失败伪装成不可绕过的技术权限。
- 前端需要支持摘要条目到准确证据的逐层展开，后端需要保证证据与候选的不可变绑定。
