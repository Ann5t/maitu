# 0030：Session 按资源排队并受全局 AI 预算约束

- 状态：Accepted
- 日期：2026-08-24
- 置信度：高

## 背景

一台中等性能服务器可能同时拥有多个已经批准、依赖满足的叶子 Session。让它们全部立即启动会争抢 CPU、内存、Worker 和 AI Provider 并发；只允许一个 Session 又会浪费可用资源。系统还需要在用户不盯着页面时限制 AI Token 与费用，但不能依赖临时浏览器状态。

## 备选方案

- 所有合格 Session 立即并发运行，由操作系统自行争抢资源。
- 全系统固定一次只运行一个 Session。
- 使用持久队列、资源感知并发和实例级 AI 预算。

## 决定

调度器根据枝干依赖、等待状态、CPU、内存、磁盘、可用 Worker、工具限制和 AI Provider 并发计算当前可运行集合。只启动资源允许的 Session，其余 Session 保持持久排队；服务重启、网页关闭或客户端断线不能丢失队列位置。

普通队列按用户批准 Session 的时间先后运行。用户可以对排队项执行“优先运行”；它只改变尚未派发工作的调度优先级，不在不可分割行动中间强行抢占运行中的 Session。同一优先级内仍按批准时间保持稳定顺序。

管理员为整套 Fudian 设置 AI Token 或费用的提醒线与硬上限，所有项目默认共同继承该实例边界。达到提醒线时继续运行并通知；达到硬上限时，不再发起新的 AI 调用，相关 Session 在安全边界保存状态并等待管理员处理。调整上限或进入新的计量周期后可以恢复，不需要重建 Session。

预算事件必须记录连接、模型、Session、实际用量、Provider 返回的费用信息和计量时间，但项目 Agent 不得读取凭据。具体 Provider 计价换算、计量周期以及是否允许项目设置更低上限留给实现前的配置设计。

## 影响

- 并行度随服务器和工具资源变化，不写死为某个 Agent 数量。
- 排队顺序默认可预测，用户仍能处理真正紧急的目标。
- AI 硬上限只暂停需要新 AI 调用的工作，不把数据或队列变成失败状态。
- 调度状态、资源租约和用量记录都必须持久化并可恢复。
