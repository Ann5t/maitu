# 0021：第一版由 Fudian 独占写入项目 GitHub 仓库

- 状态：Accepted
- 日期：2026-08-24
- 置信度：高

## 背景

如果用户、GitHub 网页、机器人、其他电脑和 Fudian 服务器都能修改同一个远端 branch，系统必须持续拉取外部提交，并处理外部更新与运行中目标枝干的时序、冲突和权限来源。这会在第一版引入一整套尚无实际需求的多写入同步协议。

用户提出第一版先假设只有当前 Fudian 服务器操控对应 GitHub 仓库。GitHub 主要用于项目远端保存、查看、克隆和 CI，不作为另一个并行编辑入口。

## 备选方案

- 支持任意外部提交并持续轮询、自动整合。
- 把 GitHub 当作权威端，每次以远端内容覆盖本地。
- 第一版采用 Fudian 单写模式，远端意外变化视为异常漂移。

## 决定

一个项目绑定 GitHub 后，第一版只允许绑定它的这一套 Fudian 实例写入该仓库的 branches。用户可以查看和克隆仓库，GitHub CI 可以读取提交、运行检查并发布状态，但用户不从网页或其他电脑直接提交、合并或推送，机器人和第二套 Fudian 也不能写 branch。

从已有 GitHub 仓库创建项目时，Fudian 在只读检查与 ProjectProposal 中固定准确的远端、默认 branch 和起始 commit；Proposal 获批并完成接管后进入单写模式。

Fudian 不能仅凭约定盲目强推。每次 push 前必须 fetch 并比较远端 ref 与本地记录的最后已知远端 commit，只允许预期的 fast-forward 更新。远端出现未知提交、force-push、ref 删除或归属变化时，自动推送进入等待状态并通知用户；系统保留本地内容，不自动覆盖远端，也不自动创建整合 MergeGate。恢复必须先由用户确认远端来源和处理方向。

## 影响

- 不需要后台持续轮询和自动吸收外部提交，运行中的子目标不会突然受到未审核远端修改。
- 自动推送仍具有 compare-and-swap 式保护，不会因错误假设破坏远端内容。
- GitHub 网页编辑、外部 PR 合并、多人直接 push 和多 Fudian 实例写入暂不支持。
- 以后需要协作时必须通过新的设计明确远端提交如何进入目标图、由谁审核以及怎样通知活动枝干，不能悄悄放宽单写约束。
