# 0015：待我处理是来源状态的汇总视图

- 状态：Accepted
- 日期：2026-08-24
- 置信度：高

## 背景

用户要求 Agent 在暂停后明确通知，并能回到现场查看和处理。现有实现除修改 Session、Proposal、ReviewGate 或 ActionRun 状态外，还创建独立 `goal_attention_items`，通知记录又引用该对象。这样同一次等待在来源对象、AttentionItem 和 Notification 中拥有多份状态，可能出现 Session 已恢复而待办仍开放等不一致。

## 备选方案

- 继续以独立 AttentionItem 作为权威待办。
- 只发送邮件或站内通知，不持久化来源的等待原因。
- 来源对象保存权威等待状态，“待我处理”作为汇总投影，通知只负责投递。

## 决定

目标模型不再包含独立 `AttentionItem` 业务对象。需要用户处理时，实际来源对象自身进入明确等待状态并保存请求内容：

- 目标草稿等待开始批准；
- Session 等待判断、异常处理或恢复；
- MergeGate 等待整合选择或最终决定；
- 工具、插件或外部操作等待授权。

请求内容至少包含原因、最后安全检查点、已尝试办法、风险、用户需要做什么、建议动作和恢复条件。用户操作直接作用于来源对象，并追加事件；不能先“完成待办”再另行同步真实状态。

站内“待我处理”是对这些来源状态的查询投影。实现可以为性能维护可重建索引或缓存，但它们不拥有 open/resolved 业务状态。站外邮件和站内提醒保留幂等 outbox、投递、送达与已读记录，但这些记录只引用来源对象，不决定它是否仍在等待。

已经合入父枝干后发给其他 Agent 的父更新通知属于 Git 状态同步消息，不是用户 Attention，本决定不删除它。

## 影响

- 用户仍能收到暂停提醒，并从统一入口回到准确现场处理。
- 待处理数量和状态不会与 Session、MergeGate 等真实状态产生双写漂移。
- 当前 `goal_attention_items`、相关外键、写入/关闭逻辑、ContextSnapshot 目录和前端列表是待迁移的兼容实现。旧记录继续可读，已发布迁移不改写；新模型启用后不再创建新的 AttentionItem。
- 通知系统仍需可靠重试、去重和投递审计，删除 AttentionItem 不等于删除 Notification/Outbox。
- 暂停在目标图上显示为节点、标记或详情，仍由可替换图投影决定。
