# 0016：Proposal 是原对话中的版本化提案卡

- 状态：Accepted
- 日期：2026-08-24
- 置信度：高

## 背景

Proposal 来源于用户和 AI 的连续讨论。若系统在 AI 给出提案后跳转到新的审批页面，要求用户接受或退回，再返回原对话修改，会丢失对话节奏和现场感；“退回”还会把自然的协商错误建模成一次失败流程。

用户希望看到类似聊天消息中的专属 Proposal 卡：同意就结束这次讨论并执行，不同意就留在原处继续商量，由 AI 给出更多版本。

## 备选方案

- 对话结束后跳转到独立 Proposal 审批页。
- 在聊天中只显示摘要，仍要求去另一页决定。
- Proposal 作为原对话中的版本化卡片，讨论、修订和接受都不离开现场。

## 决定

ProjectProposal、BranchProposal 和目标说明修订 Proposal 统一采用原对话内交互。AI 生成 Proposal 时，在当前消息流中插入一张专属卡片；卡片默认只显示目标、关键边界、重要推断、未知项和将要发生的动作，完整结构按需展开。

每一版 Proposal 都是不可变快照。用户不同意时无需点击“拒绝”或填写退回表单，直接继续用自然语言反馈；AI 生成新版本后，旧版本标记为已被替代并折叠保留。只有当前版本可以被接受，接受命令必须绑定准确 revision ID，并在版本已变化时拒绝旧操作。

接受当前版本会关闭本次 Proposal 讨论的写入入口，历史仍可查看，并原子执行该 Proposal 对应的领域转换。转换成功后界面才进入新项目、新目标枝干或更新后的目标现场；转换失败则保留对话和当前卡片，不产生半完成对象。用户确实不再考虑整个提案时可以显式取消。

MergeGate 采用相同的“不离开现场、可以继续追问”体验，但仍遵循冻结候选、整合、审核和最终决定语义，不被改名为普通 Proposal。

## 影响

- 用户不会在对话、表单和审批页面之间来回跳转。
- Proposal 仍保留准确版本、来源和人工授权证据，不因聊天式交互降低审计强度。
- 前端需要支持当前卡片固定、旧版本折叠、按需展开、移动端底部弹层和过时接受保护；具体视觉由原型验证。
- 当前 `proposal.submit`、独立审批页面、拒绝表单和相关状态投影需要迁移或转为兼容接口；旧 Proposal 修订及决定继续可读。
