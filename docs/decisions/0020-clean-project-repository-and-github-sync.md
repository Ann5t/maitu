# 0020：项目仓库保持纯净并自动同步获批更新

- 状态：Accepted
- 日期：2026-08-24
- 置信度：高

## 背景

每个 Project 已经确定使用独立 Git/Git LFS 仓库，并可以绑定自己的 GitHub 远端。还需要决定项目从何处建立、Fudian 的目标图和对话是否作为隐藏文件混入项目仓库，以及用户接受成果后是否还要手动点击推送。

完整 Fudian 工作现场已经由单项目备份负责迁移，因此没有必要为了恢复对话而污染普通项目文件。用户也希望新项目与已有 GitHub 项目都能进入系统，并减少每次接受更新后的重复同步操作。

## 备选方案

- 每个仓库强制包含 `.fudian/` 目录并保存目标图、对话和审批状态。
- 项目仓库只保存真实项目文件，Fudian 状态保存在数据库和完整备份中。
- GitHub 永远只允许手动推送。
- 绑定后自动推送所有本地 branches 和检查点。
- 绑定后只自动推送已经用户接受并进入默认 branch 的更新。

## 决定

创建项目时同时支持两种来源：建立新的空 Git 仓库，或者在用户授权后克隆已有 GitHub 仓库并从其当前默认 branch 建立根 GoalBranch。

Fudian 不向项目仓库强制加入保存目标图、Session 对话或审批状态的私有目录，也不规定所有项目必须有统一的 `docs/`、`src/` 布局。仓库只保存该项目真正需要随 Git 分叉、审查和发布的文件；Fudian 内部状态由 PostgreSQL 管理，并通过完整项目导出备份。

项目成功绑定 GitHub 后，用户已经接受且使默认 branch 前进的更新默认自动推送。用户可以在项目设置中关闭自动推送，之后使用明确的手动同步动作。普通自动同步不推送内部 GoalBranch、未决 MergeGate、未审核候选或工作中检查点。

推送是接受后的外部同步阶段，不是本地接受事务的一部分。推送失败不能回滚已经接受的 merge 或项目状态；系统保存失败状态、原因和幂等重试入口，并让用户在原项目现场处理。首次绑定、远端地址变化和凭据授权始终需要用户明确操作。

## 影响

- GitHub 仓库在 Fudian 之外仍是正常、易读的项目，不暴露完整工作对话。
- 新项目和已有仓库使用同一后续目标枝干模型。
- 正常使用不需要每次接受后再手动推送，但用户仍可关闭自动行为。
- GitHub 默认 branch 只收到用户已经接受的状态；完整内部历史依靠项目备份，不依靠远端隐藏 branch。
- 从 GitHub 获取外部新增提交、远端分歧和强制推送的处理规则仍需单独确定。
