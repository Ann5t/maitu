# 0043：运行材料默认保留并先显示空间影响

- 状态：Accepted
- 日期：2026-08-24
- 置信度：高

## 背景

项目历史、可重建工作现场和临时运行材料具有不同的恢复价值，但在没有真实使用数据前直接规定“日志保留 30 天”等期限只是猜测。用户更希望默认保留现场，先看到它们实际占用多少空间、清理后会失去什么，再主动决定。

中等性能服务器仍需要避免磁盘耗尽。空间保护不能通过后台静默删除用户可能还要查看的 Agent 输出、浏览器 Trace 或 worktree 来实现。

## 备选方案

- 所有文件永久保留且不做空间统计或磁盘保护。
- 为每类日志、缓存和 worktree 预先设置固定天数并自动删除。
- 默认保留，按恢复语义分类并显示实际占用、可释放量和增长估算，由用户主动清理。

## 决定

服务器存储按三类表达：

1. **持久项目与系统事实**：PostgreSQL 中的对话、Proposal、决定、事件和配置，项目 Git/Git LFS、长期 Evidence 文件及必要环境清单。它们属于备份和恢复承诺，不能被普通空间清理自动删除。
2. **可重建现场**：worktree、可重新取得的共享工具层和依赖缓存等。释放前必须存在经过验证的 Git 安全检查点、版本清单或重新取得来源，并明确说明恢复成本。仍被活动 Lease 或无法重新取得的环境使用时不可清理。
3. **临时运行材料**：尚未选入项目 Git/Git LFS 的完整终端输出、浏览器 Trace、截图、Runner 输出和其他调试现场。它们默认继续保存在当前服务器，但不因此成为项目版本或备份承诺；需要长期引用时仍必须导入项目仓库。

第一版不按年龄自动删除上述可重建现场或临时运行材料，也不预设固定保留天数。终态枝干仍按已有规则释放物理 worktree，因为其 Git ref 和安全 commit 已经定义了完整重建路径；其他释放和不可逆清理由用户或管理员明确发起。

存储界面至少显示实例总实际占用，并分别统计 PostgreSQL、项目 Git、Git LFS、worktree、插件与工具环境、运行记录、缓存、临时上传和备份。共享层只在实例总量中计算一次，项目视图必须标明独占量与共享量，不能把同一层重复摊入多个项目制造虚假总数。

界面同时给出当前可安全释放量、每类清理的后果和粗略增长估算。增长估算来自本实例近期实际变化，数据不足时显示区间或“尚无法估算”，不能给出虚假精确的剩余天数。释放缓存或 worktree前说明怎样重建；删除完整运行材料属于不可逆动作，必须另行确认，并保留其已经形成的结构化命令、结果、摘要和内容哈希。

磁盘空间偏低时系统先通知管理员并展示建议顺序，不自动执行清理；达到无法安全继续写入的临界状态时，新的大文件写入和相关 Agent 行动在安全检查点暂停，登录、查看、导出和清理入口仍尽量可用。具体提醒比例与临界值由实现阶段根据文件系统预留和压力测试确定，并可由管理员配置。

安全和隐私清理不受“默认保留”覆盖：语音转写临时录音、未完成或无主上传、明文秘密、Cookie、一次性凭据和隔离沙箱中的敏感残留仍按各自已接受的短期或立即删除规则处理。

## 影响

- 初期不会因为猜错保留天数而丢失用户想复查的工作现场。
- 用户可以先看到实际占用和可恢复性，再决定释放哪些空间。
- 运行材料在当前服务器上可能持续增长，必须实现可靠统计、低空间告警和安全暂停。
- 默认保留的临时材料仍可能在服务器故障时丢失；“还在磁盘上”不等于“已进入项目备份”。
- 未来得到真实增长数据后可以另行提出自动保留策略，但不能在本决策下静默启用。
