## 准备来源内容

1. 固定一次迁移快照，记录仓库标识、默认分支、全部可访问 refs、SHA、时间和对象数量。原库继续保留，迁移末尾再比较是否有新增内容。
2. 逐条分支评估功能、设计、工具与部署资料。记录每项的来源和去向：进入现行实现、进入来源档案，或由某项新实现接替。无论功能选择如何，原始历史保留。
3. 核对原项目实际使用的本地目录、未提交或忽略文件、数据库与成果。当前下载的源码和镜像不含这些资料；不把下载副本的干净状态当成原项目没有数据。
4. 读取实际存在的 PR 讨论、审阅、评论、附件与 Wiki，保存为可离线阅读的记录。没有的类型在清单中记录“本次未发现”，未核对的类型记录“未核对”。
5. 检查历史中的大文件、Git LFS 原件和子模块来源。不能仅保存指针后宣布原件已经迁移。真实凭据不提交到源码；必要的本机配置与运行备份按实例恢复方式单独保留。

五库的代码迁入以最终功能为单位，沿用脉图的数据库与执行记录。旧应用的数据库结构不能直接追加为五套活动系统；如果存在需要继承的用户数据，编写版本明确的转换和核对流程。

## 在同一仓库中保存

在源码里保留来源说明、材料去向、迁移清单和恢复操作。默认分支之外的内容同样列入清单，保留原始路径和提交定位。旧设计作为历史资料标注，避免被误读为当前程序已经实现。

为每个仓库生成包含全部可访问 refs 的 Git bundle，保留原始 Git 对象和 SHA。需要归档的 bundle、大型原件和附属资料进入 Maitu 同仓库的迁移 Release；清单保存资源名、字节数、SHA-256、访问位置和恢复方式。已经保留的源码可以从 bundle 恢复，避免在活动代码目录中堆积多个旧应用副本。

任何归档在发布前核对隐私与凭据内容，并记录未能取得的资料。私有旧库的内容只进入保持私有访问的 Maitu 仓库；不改变仓库可见性。不能以存入第三方临时下载地址代替同仓库留存。

## 恢复验收

从 Maitu Release 下载归档到一个新的空目录，实际执行以下核对，不借用旧仓库或本机镜像补齐缺失对象：

1. 逐件检查字节数和 SHA-256；验证 bundle 并恢复 Git 仓库。
2. 比较全部保存 refs、原始提交 SHA、分支文件树和 Git 对象完整性。仅能打开默认分支不足以通过。
3. 打开保存的设计、附属资料和旧成果；验证 LFS 原件、子模块和实际存在的其他内容能够读取。
4. 对迁入现行程序的能力运行对应使用验收。原库未曾验证运行的功能记录其边界，不声称旧应用可以直接启动。
5. 如果保存了运行数据，在隔离实例恢复，核对记录与成果，避免覆盖正在使用的脉图实例。
6. 重读原库快照和需要继承的本地数据。出现新增内容就补迁并重新核对受影响部分。

恢复失败、校验不一致或清单中仍有未处理内容时，该库继续保留。将恢复记录与来源清单交叉链接，避免只保存一句“备份成功”。

## 删除条件

一个旧库只有同时满足产品日用验收、该库全部可保留内容的迁移、从 Maitu 的独立恢复验收、最后一次增量核对，才报告为“具备删除条件”。给用户具体清单与已知限制，由用户决定删除；这份计划和自动校验不会执行删除。

删除 GitHub 仓库与清理本地项目目录分别处理，删除某个远端不意味着授权清理本地文件。最后保留来源仓库原链接与恢复位置，便于理解旧记录的出处。
